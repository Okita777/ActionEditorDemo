# 技能系统优化项

## 1. 当前结论

目前这一轮的主问题已经基本解决：

1. 技能运行时主链已经切到 context 机制，不再依赖 blackboard 作为正式 gameplay 数据通路。
2. `MetaSkillContext` 生命周期已经真正接入运行时，而不是只定义不落地。
3. `SkillEffectResult` 已经从“简单返回值”开始转向“正式 effect 结果载体”。
4. `Action` / `Condition` 不再在 effect 执行热路径上按节点频繁反射创建。
5. effect graph 已开始具备“加载期装配，执行期只带 context 跑”的方向。

当前不继续推进的项：

1. Buff 模板化与 Buff source lineage 深化优化，暂时停下。

---

## 2. 已完成项

### 2.1 Context 主链

已完成：

1. `SkillContext.LastEffectResult` 已移除，不再把 effect 域结果挂在 skill 域上。
2. `CurrentMetaSkillContext` / `LastMetaSkillContext` 已真正由 `MetaSkillRuntime` 管理。
3. `SkillRuntime`、`MetaSkillRuntime`、`SkillEffectRuntime` 已围绕 metaskill 结果链统一收口。
4. hitbox / bullet 的 effect 已接回主 effect executor 链路。
5. 正式逻辑已不再依赖 blackboard；blackboard 主路径已从运行时清出。

### 2.2 Action / Condition 创建路径

已完成：

1. `Action` / `Condition` 的执行热路径已不再每次按节点临时反射创建 runtime。
2. `SkillEffectRuntime` 已引入 loaded graph 缓存语义。
3. `SkillRuntime` 在角色持有技能时，已经开始预热 metaskill / hitbox / bullet 引用到的 effect graph。
4. `ActionRuntimeBase` / `ConditionRuntimeBase` 已支持可重入的 context 绑定执行，避免嵌套 effect 串上下文。

---

## 3. Context 仍可继续优化的项

这一部分不是当前阻塞项，但后续仍建议继续收。

### 3.1 四层 context 仍未完全显式化

当前问题：

1. 设计文档里已经明确了 `SkillContext / MetaSkillContext / EffectContext / ActionContext` 四层域。
2. 但实际代码里，`EffectContext` 仍更多由 `SkillEffectResult` 承担，而不是一个独立、完整、显式的 effect 域对象。

后续优化项：

1. 判断是否需要把 `EffectContext` 从 `SkillEffectResult` 中彻底拆成独立对象。
2. 明确 `EffectContext` 与 `SkillEffectResult` 的边界：
	- 哪个负责执行域状态
	- 哪个负责结果载体
3. 避免 effect 域语义长期混在 result 结构里继续膨胀。

### 3.2 ActionContext 的职责还可以继续收窄

当前问题：

1. `ActionContext` 现在已经在承担 action 结果载体职责。
2. 但 action runtime 和 action result 之间的边界还没有完全形式化。

后续优化项：

1. 继续明确 `ActionContext` 是否只表达 action 产出，不承载额外执行态。
2. 统一各个 action 的返回结果风格，避免部分 action 结果过厚、部分过薄。

### 3.3 Skill / MetaSkill / Effect 的统计结构还不完整

当前问题：

1. 当前链路已经具备聚合入口，但完整统计块体系还没有完全落地。
2. `ContextStatBlock / TargetStatBlock` 仍停留在设计层，没有系统化接入所有 action。

后续优化项：

1. 统一总量统计与按目标统计结构。
2. 明确伤害、韧性、buff、tag、属性变化的统一统计入口。
3. 杜绝未来再次出现“部分 action 走 DataContext，部分 action 走别的容器”的分叉。

### 3.4 source lineage 还没有完全统一

当前问题：

1. 文档语义已经明确：延迟 effect 不构成新的统计根。
2. 但 source lineage 在代码里还不是完整统一结构。

后续优化项：

1. 给延迟 effect 建立稳定的一套 source lineage 表达。
2. 至少统一到能明确回答：
	- 来源 skill
	- 来源 metaskill
	- 来源 effect
	- 来源 action / node
3. 为后续 hitbox / bullet / buff 归属统计做好基础。

---

## 4. Action / Condition 创建机制仍可继续优化的项

这一部分是主问题已解之后，下一层还值得继续收的地方。

### 4.1 当前是内部 graph 缓存，不是显式 loaded runtime 结构

当前状态：

1. `SkillEffectRuntime` 内部已经有 loaded graph 缓存。
2. 但 `LoadedSkillRuntime / LoadedEffectGraph` 还没有提升成显式、独立、稳定的公开运行结构层。

后续优化项：

1. 把当前内部缓存结构正式抽出来。
2. 让“加载态结构”和“执行态结构”在类型层面彻底分开。
3. 减少后续继续演化时对 `SkillEffectRuntime` 内部状态的耦合。

### 4.2 Skill 持有期加载边界还可以更明确

当前状态：

1. `SkillRuntime` 构造时已经开始预热 effect graph。
2. 但这仍然是“SkillRuntime 内部顺手做的预热”，还不是一套清晰的 `LoadSkill -> LoadMetaSkill -> LoadEffects` 生命周期接口。

后续优化项：

1. 显式整理出技能装配期 API。
2. 让角色持有技能时的加载步骤更可观察、更可调试。
3. 避免未来又把别的初始化逻辑重新塞回执行期。

### 4.3 Action / Condition runtime 的最终形态还可以继续纯化

当前状态：

1. 当前已经从“每次反射创建”推进到了“节点 runtime 复用 + context 重绑”。
2. 这已经解决了主要性能问题。
3. 但 runtime 本体仍然保留了 `mContext` 绑定式写法。

后续优化项：

1. 评估是否逐步过渡到更纯的无状态执行器或执行委托。
2. 让节点执行器对 context 的依赖变成显式参数，而不是依赖内部字段。
3. 进一步降低嵌套执行和长期维护中的状态污染风险。

### 4.4 graph 预加载覆盖面还不算最终完成

当前状态：

1. metaskill 的 OnAdd / OnEnd。
2. hitbox 的 OnHit。
3. bullet 的 OnHit。

这些已经接入预热。

后续优化项：

1. 如果后续 bullet 扩展出 `OnSpawnEffect`、`OnExpireEffect` 等正式入口，需要统一纳入同一套预加载链。
2. 任何新增 effect 挂点都必须遵守“加载期装配，不在执行期临时解释”。

### 4.5 graph 缓存的生命周期管理还可以补强

当前状态：

1. graph 已有缓存。
2. 但缓存何时建立、何时失效、何时刷新，还没有形成完整策略。

后续优化项：

1. 明确缓存生命周期归属：
	- 跟随 SkillRuntime
	- 跟随全局 SkillConfig
	- 或跟随资源重载
2. 明确编辑器热重载、资源重载、运行时重新装配时的缓存失效策略。

---

## 5. Buff 相关项

当前状态：

1. Buff 不再作为这轮继续推进项。
2. 已做的只有最小接入：Buff effect 可以复用当前主 effect executor 机制。

暂缓项：

1. `LoadedBuffTemplate` 模板化。
2. Buff 完整 source lineage。
3. Buff delayed effect 的正式归属统计。
4. Buff 专属 graph 缓存生命周期设计。

说明：

1. 这些项不是不要做。
2. 只是当前主问题已经解决，后续应单独开一轮处理，不与本轮主链改造混在一起。

---

## 6. 后续建议顺序

如果后面继续优化，建议顺序如下：

1. 先把 loaded runtime 结构正式显式化。
2. 再把 context 四层域继续收完整，尤其是 effect 域和统计块。
3. 最后单独开 Buff 模板化和 source lineage 归属链改造。

这样做的原因是：

1. 主 effect 执行结构先稳定。
2. context 聚合边界再收紧。
3. 最后再处理 Buff 这类生命周期更复杂的延迟载体，风险最低。
