# SkillEditor 阶段性总结

## 1. 文档目的

本文档用于总结当前 `SkillEditor` 的阶段性进度，明确：

- 现在已经完成了什么
- 哪些能力已经有基础但还需要验证或补完
- 哪些设计决策仍未最终确定
- 接下来建议优先推进什么

这不是最终设计文档，而是一份面向后续开发的阶段性结论文档。

## 2. 当前阶段判断

当前 `SkillEditor` 已经不再只是一个“技能编辑器原型”，而是已经具备了正式扩展价值的基础系统。

从整体上看，当前系统已经完成了最关键的几条主链：

- `Skill -> MetaSkill -> Timeline -> Effect -> 动画桥` 的正式运行时链路
- `Skill` / `MetaSkill` 的可视化配置入口
- 预览单位驱动的正式预览路径
- 技能级 CD / Cost / 连段 / 后摇 等关键规则的第一版落地

现阶段最重要的变化，不是“功能越来越多”，而是系统的核心边界已经逐渐清晰：

- `Skill` 负责更高层的技能语义、切段、连段、CD、消耗
- `MetaSkill` 负责单段技能的执行细节
- `Timeline` 负责该段技能中的命中盒、子弹、事件等时序内容
- 动画桥负责将技能系统和单位动画载体连接起来
- 预览系统尽量走正式运行时，而不是额外造一套测试逻辑

这意味着当前系统已经进入“可以持续做系统化补完”的阶段，而不是继续堆实验性功能的阶段。

## 3. 当前已完成的核心内容

### 3.1 技能主运行时链路已经建立

当前已经具备以下正式能力：

- `SkillRuntime` 可按事件驱动 `Skill` 内部节点切换
- `MetaSkillRuntime` 可执行单段技能逻辑
- `MetaSkillTimelineRuntime` 可驱动 `Timeline` 中的轨道条目
- `SkillEffectRuntime` 可执行效果树
- `SkillCharacterActionBridge` 已经接入 Animancer，并承担技能动画桥接职责

这条主链目前已经能够支撑一个技能从输入触发，到切入对应 `MetaSkill`，再到播放动画、触发时序条目、执行效果的完整流程。

### 3.2 Skill 级 CD / Cost 已经正式落地

当前已经完成：

- `Cooldown` 从 `MetaSkill` 移到 `Skill`
- `Cost` 从 `MetaSkill` 移到 `Skill`
- `Cost` 支持多资源消耗
- 当前资源类型已有 `Mana` / `Hp`
- `Skill` 编辑器已支持直接配置这些内容

这一步非常关键，因为它明确了：

- `MetaSkill` 是技能中的一段
- `Skill` 才是完整技能的资源和冷却归属对象

### 3.3 连段与断连逻辑已完成第一版

当前已经完成：

- CD 从第一段开始计时
- 连段过程中，Skill 级 CD 不会阻断续段输入
- 已支持断连超时配置 `ComboContinuationTimeout`
- 超时未续段时，整条 `Skill` 正式断连并回到剩余 CD 控制
- 执行阶段不允许被自己的后续技能提前打断

这意味着当前连段技能已经具备了较为合理的基础行为。

### 3.4 MetaSkill 已拆分为执行阶段与后摇阶段

当前已经完成：

- `MetaSkill` 增加了 `Recovery` 配置
- 执行阶段与后摇阶段已经成为正式运行时概念
- 后摇阶段只负责播放 recovery 动画
- 执行阶段内，同技能输入仍被阻断
- recovery 阶段允许同技能取消

这是后续打断、取消、技能派生规则的基础。

### 3.5 动画预览与运行时动画桥都已补齐第一版

当前已经完成：

- `MetaSkillTimelineEditorWindow` 已支持完整流程预览
- 编辑器内可以预览执行动画 + 后摇动画的连续流程
- 运行时动画桥已改为优先走 Animancer 过渡，而不是“硬停再播”
- `controller -> 技能 -> recovery -> controller` 的动画切换方向已经正确

这意味着技能动画现在已经不只是“能播”，而是开始具备可调和可用的过渡能力。

### 3.6 SkillGraph 的基础体验已明显改善

当前已经完成：

- `Entry` / `Exit` 节点可移动，位置可保存
- 连线支持默认事件
- `MetaSkill -> 下一个节点` / `MetaSkill -> Exit` 的空事件连线默认走 `OnMetaSkillEnd`
- `Entry -> 节点` 可默认走起手事件

这让图编辑过程更接近真正的技能制作流程，而不是被大量样板配置拖累。

## 4. 当前最大的系统特点与核心价值

当前系统最重要的特点，是“技能本体可以尽量独立于具体载体和具体角色逻辑来制作”。

这件事的价值非常大，因为它支撑的是一个更高层的目标：

- 玩家可自行组合技能
- 技能可被不同角色装配
- 技能本体尽量不被某个固定角色脚本绑定死

这个方向是正确的，也是当前系统最值得坚持的主线。

但正因为技能系统被设计得更可插拔，就必须尽快回答一个新的问题：

> 技能系统应该如何被外部系统调用？

也就是：

- 玩家输入如何调用它
- AI 如何调用它
- Action 系统如何调用它
- 被动事件如何调用它

这会是下一阶段最重要的架构问题之一。

## 5. 你当前最在意的问题：逐项判断

下面按当前最关注的问题逐项总结。

### 5.1 技能系统如何外接其他系统（AI / Action / BT）

这是当前最重要、也最需要尽快明确边界的问题。

当前判断：

- 当前技能系统本身已经具备被外部调用的基础
- `SkillRuntime.Trigger(...)` 这一层，天然适合作为外部系统触发技能的入口
- 现阶段最不应该做的，是让 AI 直接依赖编辑器层或具体载体细节

当前建议：

- 先定义一层“技能调用接口 / SkillInvoker / SkillCommandAdapter”
- 由 BT、AI、玩家输入、Action 系统统一通过这层发起技能请求
- 不要急着把技能系统直接绑死在 `AsiActionEditor` 某个内部流程上

关于 AI 的选择，当前建议优先级如下：

1. 先用 BT 或一个简单 AI 调用适配层驱动技能
2. 再评估 `AsiActionEditor` 是否适合作为更上层的动作组织系统
3. 如果后续发现“角色不可变部分”越来越复杂，再单独扩展自己的 Action 系统

当前阶段不建议：

- 现在就把 AI 绑定死在 `AsiActionEditor`
- 现在就重写一整套更大的 Action 框架

当前阶段最合理的目标应该是：

- 先证明技能系统可以稳定被“外部决策系统”驱动
- 再决定外层最终选 BT、AsiActionEditor 还是混合模式

### 5.2 攻击盒能否正常运转

当前状态：有基础，但必须继续做真实验证。

已具备：

- `HitBoxConfig`
- timeline 轨道编辑
- 场景预览与烘焙预览
- `MetaSkillTimelineRuntime` 中对 hit box 的时序触发
- `OnHitEffect` 挂点

当前尚不能直接下“完全可用”的结论，原因不是配置侧不完整，而是需要继续验证：

- 不同挂点来源下的位置是否稳定
- duration 型与瞬时型攻击盒是否都正常
- 重复命中逻辑是否符合预期
- 命中结果是否能稳定流入 battle / effect 层

判断：

- 配置链和运行链已经有了
- 现在进入“战斗实测和修正阶段”

#### 当前补充：weaponPoint / weaponConfig 挂载方案

关于武器挂载，当前后续统一方案已经明确，建议直接按这套方式推进，不再继续扩散旧方案：

- 角色骨骼上有固定的 `weaponPoint`，动画直接使用这个骨骼点
- 武器资源需要配置 `SkinnedMeshRenderer`
- 武器数据由 `weaponConfig` 描述
- 当预览单位配置了 `weaponConfig` 后，编辑器预览会把武器创建到角色层级下，并把武器的 `SkinnedMeshRenderer` 绑定到 `weaponPoint`
- 正式运行时也采用同一套逻辑：装备武器 / 切换武器，本质上就是设置 `weaponConfig`，创建武器对象，并把武器的 `SkinnedMeshRenderer` 绑定到 `weaponPoint`

这套方案的优点是边界比较清晰：

- 技能侧不再依赖一组额外武器挂点系统
- 预览与运行时使用同一挂载语义
- 后续攻击盒、子弹、特效如果要依附武器表现，可以优先围绕 `weaponPoint` 和武器实例本身来组织

因此当前建议是：

- `weaponPoint` 作为角色标准武器骨骼点保留下来
- `weaponConfig` 作为武器创建与表现绑定入口
- 技能 Timeline 中与武器相关的挂载逻辑，后续尽量围绕这套统一方案收敛

### 5.3 子弹的运转

当前状态：有配置与触发基础，但仍属于待验证重点。

已具备：

- `BulletConfig`
- timeline 编辑入口
- runtime 触发入口
- `OnHitEffect`

需要继续确认：

- 子弹实体的生命周期是否完整
- 命中判定是否稳定
- 命中后效果是否闭环
- 与挂点 / 朝向 / 目标的关系是否足够清晰

判断：

- 子弹不是空白功能，但还不能视为完全收口

### 5.4 Effect 能否正常触发

当前状态：基础已经建立，是目前相对靠前的一块完成面。

已具备：

- `SkillEffectConfig`
- 效果树编辑器
- `MetaSkill.OnAddEffect`
- `MetaSkill.OnEndEffect`
- `HitBox.OnHitEffect`
- `Bullet.OnHitEffect`
- runtime 执行器 `SkillEffectRuntime`

当前还需要继续做的是“覆盖测试”，而不是重新设计：

- 不同入口的 effect 是否都能稳定触发
- 条件节点 / 动作节点 / 顺序节点在复杂组合下是否稳定

判断：

- effect 系统已经不属于“未开始”，而是“核心链已通，需要做真实覆盖验证”

### 5.4.1 Timeline 轨道仍有缺口：特效轨道 / 音效轨道 / 摄像机轨道

当前判断：这三类轨道里，摄像机轨道先不做；特效轨道和音效轨道需要进入正式规划，而且实现策略应尽量直接兼容 `AsiActionEditor`。

原因很明确：

- 摄像机轨道往往会牵扯镜头管理、角色锁定、关卡镜头、Cinemachine 或其他外部系统
- 这部分现在会明显扩大边界，不适合作为当前战斗主链验证阶段的插入项
- 特效轨道与音效轨道则更接近技能时序本体，属于技能 Timeline 内天然应该补齐的轨道能力

这里需要特别定一个原则：

- 特效轨道和音效轨道，优先直接参考并兼容 `AsiActionEditor`
- 能照抄就照抄，能不改就不改
- 只有当 `SkillEditor` 现有运行时结构与其实现方式存在明确冲突时，才做最小调整

从当前参照结果看，`AsiActionEditor` 已经有比较清晰的基础：

- Timeline 事件枚举里已有 `EET_Audio` 与 `EET_Partocle`
- 运行时有 `ActionEditor_Audio` 组件负责按 source/group/clip 方式播放音效
- 运行时有 `ActionEditor_Effects` 组件负责特效对象组织与播放
- 编辑器侧也已有对应的 inspector / preview / event 更新逻辑

因此对 `SkillEditor` 的结论不是“自己重新设计一套更漂亮的轨道”，而是：

- 优先把 `AsiActionEditor` 的音效轨道、特效轨道的数据形态、运行时触发方式、编辑器交互方式摸清并迁入
- 迁入时尽量保持字段语义、资源引用方式、播放习惯一致
- 让 `SkillEditor` 的 TimelineRuntime 只承担“在正确时间调用它们”，而不是发明一套额外抽象

但当前优先级仍然不能被这件事打乱。

现在最重要的不是先把轨道补满，而是先验证：

- 攻击盒是否稳定命中
- 子弹是否稳定闭环
- effect 是否能从多个入口稳定触发

只有这三条先跑通，战斗核心链路才算真正打通。特效轨道和音效轨道应当作为“下一批立即要补的 Timeline 能力”，但不应抢在战斗核心验证之前。

### 5.5 打断窗口是否可用

当前状态：第一版已落地，但还没有形成完整结论。

已具备：

- `SetInterruptWindow` 事件配置
- runtime 执行路径
- bridge 中断窗口状态同步
- recovery 阶段默认可打断逻辑的第一版接入

还未完全做完的是：

- 打断窗口与外部状态系统的正式消费闭环
- 打断后的状态回退 / 转出规则
- “被谁打断、何时打断、如何转出”的统一规范

判断：

- 不是没有，而是“机制基础已在，系统收口未完成”

### 5.6 根运动是否需要支持

当前状态：这是一个未定方向，但很重要。

当前建议：

- 不要立刻把 root motion 作为所有技能的硬绑定能力塞进系统
- 先通过单位事件或动画桥扩展，让“是否使用位移驱动”保持可插拔

原因：

- 有的技能需要 root motion
- 有的技能更适合靠力 / 位移事件 / 状态系统移动
- 如果现在把 root motion 做成统一刚性方案，后续动作类型一复杂就容易受限

判断：

- 需要支持，但应作为“动作驱动能力”统一设计，而不是零散加在单个技能参数里

### 5.7 单位事件中的力扩展

当前状态：已有基础，值得继续扩。

已具备：

- `ApplyForce` 事件类型
- 基本的方向 / 局部空间参数

后续建议增强：

- 区分瞬时力 / 持续位移 / 冲刺
- 增加更多坐标来源
- 增加更清晰的力作用目标
- 视需要增加曲线 / 分段参数

判断：

- 已有雏形，但如果要承担更多移动能力，需要升级成更正式的“单位运动事件”能力

### 5.8 IK 支持（翻墙、贴墙跑等）

当前状态：现在还不应该直接做。

原因：

- 这类能力不只是技能问题
- 本质上会同时依赖：环境检测、位移/力、动作状态管理、IK 修正、可能还要有专门 locomotion/action 规则

判断：

- IK 不是当前技能系统的短期缺口
- 它应该放在“高级运动能力系统”里统一规划

当前建议：

- 先把技能系统中“力 / 动画桥 / 事件扩展”这些地基打稳
- 再决定是否进入 wall run、vault、mantle 这类高级运动能力

### 5.9 被动技能事件能否正常运作

当前状态：有分类和装配基础，但事件源体系未完整。

已具备：

- `SkillCastCategory.Active / Passive`
- 预览单位中的主动槽 / 被动槽数据结构
- 被动技能装配入口基础

尚缺：

- 被动技能正式事件源
- 生命周期事件 / 战斗事件 / 属性事件 的统一派发方式
- 被动技能何时被激活、何时监听、何时失效的清晰规则

判断：

- 当前被动技能属于“数据层和装配层有了，触发系统还没做完”

### 5.10 Buff 系统

当前状态：接口和 effect 节点已经预留，但正式实现还没有真正完成。

已具备：

- `IBuffService`
- `HasBuff` 条件
- `AddBuff` / `RemoveBuff` 动作
- 编辑器配置入口

尚缺：

- 真实 Buff 容器实现
- Buff 生命周期
- Buff 叠层 / 刷新 / 覆盖规则
- Buff 与属性 / Tag / 被动技能 / UI 的关系

判断：

- 这是非常明确的“下一阶段重点系统”

### 5.11 Tag 系统正式设计

当前状态：已有 `TagContainer`，但还只是轻量级容器，不是完整体系。

当前问题：

- Tag 的命名规范未定
- Tag 的层级与作用域未定
- Tag 和 Buff / State / Skill / MetaSkill / Action 的关系未完全定义

建议方向：

- 先把 Tag 作为统一语义标记层
- 不把 Tag 当成 Buff 替代品
- 不把 Tag 当成状态系统替代品
- 明确 Tag 只负责“语义标记与查询”

判断：

- Tag 应尽快从“字段存在”升级到“正式规范存在”

## 6. 未来阶段建议：按优先级推进

### 阶段 A：把当前战斗主链验证扎实

建议优先完成：

- 攻击盒真实命中验证
- 子弹真实命中验证
- effect 入口覆盖验证
- 打断窗口真实消费验证
- recovery / cancel / transition 的实战验证

这一阶段要明确一个重点：

- 攻击盒、子弹、effect 是当前最高优先级
- 这三块一旦稳定，战斗核心链路就真正打通了
- 其他新增轨道和外围能力，都不应抢在这一步之前分散精力

目标：

- 让当前已经存在的主链变成“可依赖”的主链

### 阶段 B：明确技能系统的外部调用边界

建议优先完成：

- 设计统一的技能调用适配层
- 让 BT / AI / 玩家输入 / Action 系统都通过同一入口调技能
- 先用一个简单 AI 场景证明 NPC 可以稳定释放固定技能

目标：

- 回答“技能系统如何外接其他系统”这个最大的不确定点

### 阶段 C：补齐 Timeline 缺失轨道

建议优先完成：

- 特效轨道
- 音效轨道
- 明确两者的资源引用、运行时触发、预览方式

这一阶段的实现原则需要写死：

- 直接参考 `AsiActionEditor`
- 能兼容就兼容，能照抄就照抄
- 不主动做额外抽象和创新
- 只有在 `SkillEditor` 运行时边界不兼容时，才做最小必要改造

摄像机轨道当前不进入这一阶段，原因是它会过早牵涉外部镜头系统。

目标：

- 补齐技能 Timeline 在表现层最刚需的两类轨道
- 让技能制作不再只覆盖命中和逻辑，也能覆盖正式的音画时序

### 阶段 D：补齐状态型系统基础设施

建议优先完成：

- Buff 系统正式实现
- Tag 系统正式规范
- 被动技能事件源体系

目标：

- 让技能系统从“主动释放技能系统”升级为“完整战斗技能系统”

### 阶段 E：进入高级动作能力

建议在前几阶段稳定后再考虑：

- 根运动策略
- 单位运动事件增强
- IK 支持
- 高级动作能力（翻墙、贴墙跑等）

目标：

- 让技能系统与更复杂的角色运动 / 动作表达融合

## 7. 当前最值得坚持的原则

后续开发建议继续坚持以下原则：

### 7.1 技能系统尽量保持可插拔

技能系统要尽量作为“可被外部系统调用的可变能力层”，而不是直接变成某个角色脚本的附属品。

### 7.2 预览尽量走正式运行时

不要为了预览额外造一套假的逻辑。

预览工具可以存在，但应尽量复用真实运行时的链路和规则。

### 7.3 Action / Skill / State / Buff / Tag 要各司其职

后续一定要避免职责混淆：

- `Skill` 不是状态系统
- `Tag` 不是 Buff
- `Buff` 不是 Action
- `Action` 不应该替代技能配置系统

如果这些边界后续继续保持清晰，系统会越做越稳；如果这些边界开始混，系统会很快失控。

## 8. 当前结论

当前 `SkillEditor` 最大的好消息不是“做了很多东西”，而是：

> 已经完成的这些东西，开始形成一个真正有扩展前景的整体系统了。

现在最适合做的事，不是继续盲目加新点，而是：

- 把当前主链验证扎实
- 优先打通攻击盒 / 子弹 / effect 这三条战斗核心链
- 把外部调用边界设计清楚
- 按 `AsiActionEditor` 兼容策略补齐特效轨道与音效轨道
- 把 Buff / Tag / Passive 这些系统基础设施补齐

一旦这些完成，这套系统就会从“好用的技能编辑器”进一步走向“完整的角色战斗能力系统”。
