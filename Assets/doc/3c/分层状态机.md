# 分层状态机设计与落地方案

> 本文档为旧版方案记录，最新方案请优先参考 [分层状态机_v2.md](Assets/doc/3c/分层状态机_v2.md) 与 [SkillRuntime第四版最小分层状态机数据结构草案.md](Assets/doc/SkillRuntime第四版最小分层状态机数据结构草案.md)。

## 1. 这份文档要解决什么

这份文档不是再重复设计哲学，也不是直接给最终完整 3C 终局类图。

它只解决当前最现实的问题：

1. 当前项目已经有一个可运行的单层 [StateController.cs](Assets/SkillEditor/Runtime/Runtime/State/StateController.cs)。
2. 当前动画播放链路仍然是单轨状态动画，不支持真正的动画分层。
3. 项目需要开始进入分层状态机阶段，但必须尽量小改、稳改，不能把现有技能和状态 runtime 一次性推翻。

所以本文档的目标不是“重新发明一套状态机”，而是回答：

如何把现在这个单层 `StateController`，平滑改造成“单控制器、多轨道”的分层状态机，并且让它先服务动画播放与切换升级。

这份方案的核心原则是：

1. 保留一个 `StateController`。
2. 不拆成多个平级 `LocomotionStateController`、`ActionStateController` 实例。
3. 把“多层”理解为：一个控制器统一维护多条状态轨道。
4. 先支持最小必要的两条状态层：`Locomotion` 和 `Action`。
5. 先把动画播放和切换做对，再继续扩展 UpperBody、Additive 和 RootMotion 策略。

## 2. 当前项目的真实现状

### 2.1 当前 `StateController` 的问题本质

现有 [StateController.cs](Assets/SkillEditor/Runtime/Runtime/State/StateController.cs) 的结构并不差，它已经具备：

1. 状态配置表。
2. 活动状态运行时。
3. Timeline 推进。
4. 中断评估。
5. 默认下一状态跳转。
6. 技能驱动状态通知。

真正的问题只有一个，而且是结构性问题：

它把“当前活动状态”设计成了全局唯一的 `_activeState`。

这意味着整个角色任意时刻只能有一条状态主线。

这会直接导致：

1. 跑动和攻击不能同时成立，只能二选一。
2. 动画切换默认等于逻辑切换。
3. 一旦动作层接管，底盘状态事实就会丢失。
4. 动作结束后只能重新猜现在应该回到什么状态。

这正是单层状态机无法支撑高级 ARPG 动画框架的根本原因。

### 2.2 当前配置层还没有“状态所属层”概念

当前 [UnitConfig.cs](Assets/SkillEditor/Runtime/Config/Unit/UnitConfig.cs) 里的 `StateConfig` 只有：

1. `StateId`
2. `StateName`
3. `AnimationClipPath`
4. `DefaultNextStateId`
5. `Timeline`
6. `Tags`

也就是说，当前状态配置里还没有下面这些后续必须存在的信息：

1. 这个状态属于哪一层。
2. 这个状态的表现输出要写到哪个动画槽位。
3. 这个状态对其他层的表现是否有覆盖权。
4. 这个状态对移动和转向是否有接管权。

所以“分层状态机”的第一步，不是先改算法，而是先把状态的层归属补进数据模型。

### 2.3 当前动画控制接口已经具备一个好的收缩方向

前一轮已经把原先的 `ActionBridge` 收缩成纯动画控制接口，当前运行时已经通过 [ICharacterActionBridge.cs](Assets/SkillEditor/Runtime/Interfaces/ICharacterActionBridge.cs) 中的 `ICharacterAnimationController` 来做状态动画播放。

这件事很重要，因为它意味着：

1. 状态层和动画层已经有了一个可继续演化的边界。
2. 现在可以让状态机负责产生“状态与表现请求”，而不是直接持有动画实现细节。
3. 这为后续引入动画槽位系统创造了条件。

### 2.4 `AsiActionEditor` 给出的真正参考点

从 [ActionStateMachine.cs](Assets/Plugins/AsiActionEditor/Engine/RunTime/Script/AsiActionEditor/RunTime/Script/UnitController/ActionStateMachine/ActionStateMachine.cs) 和 [ActionStatePart.cs](Assets/Plugins/AsiActionEditor/Engine/RunTime/Script/AsiActionEditor/RunTime/Script/UnitController/ActionStateMachine/Part/ActionStatePart.cs) 可以看出，`AsiActionEditor` 的关键不是“做了很多控制器”，而是：

1. 一个 `ActionStateMachine` 统一持有 `AllActionStatePart`。
2. 每个 `ActionStatePart` 表示一条独立轨道。
3. 状态本身有 `AnimaLayer` 归属。
4. 命中、受击、输入检查等逻辑，是按轨道分别评估的。

这和你当前的直觉是一致的：

正确方向不是“每条层都做一个单独控制器”，而是“一个总状态机内部维护多条层级轨道”。

这个参考对当前项目最有价值的地方是：

1. 统一入口。
2. 分层活动态。
3. 分层评估。
4. 分层表现输出。

而不是照搬它的全部运行时结构。

## 3. 本项目应采用的方向

### 3.1 只保留一个 `StateController`

这一点应该明确，不要摇摆。

当前项目最合适的方向就是：

1. 仍然只有一个 `StateController`。
2. 这个 `StateController` 统一持有所有状态层的运行时。
3. 每个状态层各自有自己的活动状态、时间线和中断评估。
4. 跨层规则由这个总控制器统一协调。

这样做有几个直接好处：

1. 对现有调用面最友好。
2. 仍然可以保留统一的 `Tick` 生命周期。
3. 技能系统、Buff、输入、命中、受击这些共享上下文不用拆散。
4. 跨层关系更容易统一定义，不会变成多个控制器互相调用。

### 3.2 “状态层” 和 “动画槽” 不能混为一谈

这一点非常关键。

当前阶段不要把 `UpperBody`、`Additive` 直接等同于“必须也是一条完整状态线”。

因为：

1. `Locomotion` 和 `Action` 是逻辑状态层。
2. `UpperBody` 和 `Additive` 在当前阶段更适合作为动画输出槽，而不是完整的逻辑状态层。

也就是说，当前最稳的结构应该是：

1. 先做两条状态层：`Locomotion`、`Action`。
2. 先做多个动画槽：`Locomotion`、`Action`、预留 `UpperBody`、预留 `Additive`。
3. 由状态层决定输出到哪些槽。

这是最小改法，也是最不容易失控的改法。

如果一开始就把 `UpperBody`、`Additive` 做成和 `Action` 同等级的完整状态线，当前项目的数据配置、时间线和打断体系都会一下子复杂太多。

### 3.3 第一阶段只做两条状态层

第一阶段正式落地时，只做：

1. `Locomotion` 层
2. `Action` 层

原因很实际：

1. 这已经足够解决“动作覆盖底盘，但底盘状态事实不丢”的核心问题。
2. 这已经足够支撑“当前阶段主要解决动画播放和切换”的目标。
3. 这也是与你现有技能主线最自然的对接方式。

未来的 `UpperBody` 和 `Additive` 先作为动画输出层预留，不急着变成完整状态层。

## 4. 第一阶段的层级模型

### 4.1 状态层定义

建议先引入一个明确的状态层枚举，例如：

1. `Locomotion`
2. `Action`

后续如果真的有必要，再扩展：

1. `UpperBodyAction`
2. `Reaction`
3. `Special`

但第一阶段不要提前做这些扩展。

### 4.2 `Locomotion` 层职责

`Locomotion` 层负责角色底盘事实。

它应该回答：

1. 当前是否接地。
2. 当前底盘姿态是什么。
3. 当前是否允许常规移动。
4. 当前是否允许自由转向。
5. 当前底盘动画应该由哪个 locomotion 片段或 BlendTree 驱动。

它的典型状态包括：

1. `Idle`
2. `Walk`
3. `Run`
4. `Sprint`
5. `Jump`
6. `Falling`
7. `Land`

这条层必须长期存在，不能因为 `Action` 层进入动作就被“删除”。

这是当前单层状态机最致命的问题，也是这次改造首先要解决的问题。

### 4.3 `Action` 层职责

`Action` 层负责高优先级动作行为。

它应该回答：

1. 当前是否正在执行一个高优先级动作。
2. 当前动作是什么。
3. 当前动作处于哪个阶段。
4. 当前动作是否拥有取消、派生、打断资格。
5. 当前动作是否接管移动。
6. 当前动作是否接管转向。
7. 当前动作的表现应该覆盖哪些动画槽位。

它的典型状态包括：

1. `None`
2. `Skill_*`
3. `Dodge`
4. `HitReact`
5. `Knockdown`

这条层不是角色永久主线，而是高优先级动作线。

`Action` 结束后，它应当退出为 `None` 或无活动态，而不是把角色全局状态机重新改回 `Idle/Run`。

回到哪种底盘表现，应该由 `Locomotion` 层天然继续提供，而不是事后重建。

## 5. 层与层之间的规则

这一部分是分层状态机最核心的地方。

### 5.1 `Action` 默认覆盖表现，但不直接硬改其他层状态

这一条需要比“只覆盖表现，不覆盖状态”说得更精确。

在当前项目里，一个 `State` 不是单纯标签，而是一个由多条 `StateTimeline` 轨道组成的运行时容器。

它至少会承载：

1. 动画轨
2. 攻击盒轨
3. 子弹轨
4. 音效轨
5. 特效轨
6. 单位事件轨

因此，如果简单理解成：

1. `Locomotion = Run` 继续完整推进
2. `Action = Skill1` 只把动画盖住

那就会出现明显问题：

1. 动作期间仍然触发跑步音效
2. 动作期间仍然触发跑步相关单位事件
3. 底盘时间线副作用与当前动作表现不一致

所以当前阶段更合理、更贴合项目实际的原则应该是：

1. `Action` 状态切换时，默认不直接把 `Locomotion` 这类其他层硬改成 `None`。
2. `Action` 会声明自己的影响因素，例如锁移动、锁转向、改变底盘控制事实。
3. 其他层根据这些共享事实和自身规则，自然迁移到新的安全状态。
4. 动作对其他层的影响，优先通过“规则自然导出的状态迁移”完成，而不是现阶段额外再造一套推进策略系统。

换句话说，当前阶段推荐的做法不是：

1. `Action` 一进入，就直接跨层写死 `Locomotion` 当前状态。

而是：

1. `Action` 改变角色当前的共享控制事实。
2. `Locomotion` 根据这些事实判断 `Run` 是否仍然成立。
3. 如果不成立，就自然切到 `Idle`、`LockedIdle`、`GroundedHold` 等安全状态。

因此，正确理解应该是：

1. `Action` 默认不直接覆盖其他层的状态归属。
2. 但它完全可以通过规则，间接改变其他层的状态结果。
3. `Action` 结束后，表现层回退到其他层当前真实状态，而不是回退到一个被猜测的状态。

这才是当前项目里逻辑自洽、又能避免时间线副作用失控的做法。

### 5.2 覆盖关系应由状态声明，而不是写死在控制器里

不能简单写成：

1. `Action` 一进入就永远全身覆盖。

因为后续你明确会需要：

1. 全身动作。
2. 上半身动作。
3. 可叠加动作。

所以更合理的做法是让状态声明它的表现模式，例如：

1. `FullBodyOverride`
2. `UpperBodyOverlay`
3. `AdditiveOverlay`

第一阶段虽然只有两条状态层，但状态本身就应该带这个表现声明。

这样以后加 `UpperBody` 槽和 `Additive` 槽时，不用重新推翻状态机。

### 5.3 打断轨默认只负责同层切换

分层之后，状态机是否“平行”，关键不在于条件能否来自别的系统，而在于切换目标是否跨层污染。

当前项目的打断主链仍然应该是：

1. 当前状态读取自己的打断轨。
2. 当前状态检查打断条件是否成立。
3. 当前状态决定自己是否切到某个目标状态。

这里要明确区分两件事：

1. 打断条件来源。
2. 打断目标状态归属。

第一项可以来自很多地方：

1. 移动输入。
2. 下一技能输入。
3. 冲刺输入。
4. 受击或破防。
5. 标签、朝向、距离等运行时事实。

但第二项在第一阶段应当收紧为：

1. 打断轨默认只能指向同层状态。

也就是说：

1. `Action` 状态的打断轨，默认只应该配置 `Action` 层目标。
2. `Locomotion` 状态的打断轨，默认只应该配置 `Locomotion` 层目标。
3. 编辑器层面也应尽量按层过滤可选目标，避免配出跨层跳转。

这样设计的原因不是教条，而是为了防止状态图语义污染：

1. `MoveInput` 可以参与 `Action` 的打断判定。
2. 但 `MoveInput` 命中后，不代表 `Action` 应直接跳到 `Run`。
3. `Run` 仍然是 `Locomotion` 语义状态，不应由 `Action` 层打断轨直接调度。

因此，像“后摇可被移动打断”这种需求，推荐表达成：

1. 当前 `Recovery` 状态允许 `MoveInput` 打断。
2. 打断成功后，`Action` 层切到本层统一释放态或空态。
3. `Locomotion` 层继续按自己的规则维持 `Idle/Run/Turn/Brake` 等状态。
4. 当 `Action` 层进入释放态并结束覆盖后，最终可见表现自然露出当前底盘状态。

这比直接配置：

1. `SkillRecovery --MoveInput--> Run`

要干净得多，也更符合“分层而非伪分层”的设计目标。

### 5.4 `Locomotion` 不应该直接打断 `Action`

通常情况下，`Locomotion` 层的职责是持续更新底盘事实，而不是抢占高优先级动作。

所以第一阶段建议：

1. `Locomotion` 层只改自己的状态。
2. `Locomotion` 层不直接结束 `Action` 层。
3. `Action` 层结束后，表现自然回到底盘。

真正能主动打断 `Action` 层的，应该是：

1. 更高优先级动作。
2. 受击、硬直、击飞等强制动作。
3. 当前 `Action` 状态明确允许的取消规则。

这里还要补一条边界：

1. 默认情况下，各层不要互相硬改当前状态。
2. 少数全局强制场景，例如 `HitReact`、`Knockdown`、`Death`，允许由总 `StateController` 做统一跨层裁决。

也就是说：

1. 常规技能与动作，优先走“共享事实 -> 自然迁移”。
2. 全局强制状态，允许走“总控制器白名单式跨层干预”。

这条边界必须保留，否则系统会在“完全不允许跨层影响”和“所有层都能随便互改状态”之间来回摇摆。

### 5.5 `Action` 对移动与转向的接管必须显式声明

不要把“动作层覆盖底盘动画”和“动作层接管移动控制”混成一件事。

这两件事必须分开声明：

1. 是否覆盖表现。
2. 是否接管位移。
3. 是否接管转向。

例如：

1. 某些攻击是全身覆盖，但仍允许缓慢转向。
2. 某些闪避会接管位移，但不完全锁死朝向。
3. 某些施法只覆盖上半身，不应该影响底盘移动。

这部分虽然当前阶段不要求全部实现，但数据模型必须现在就预留。

### 5.6 状态静态属性与单位事件门禁要分层表达

当前项目已经有状态时间线和单位事件轨，这非常适合拿来表达“某个时刻开启或关闭某个门禁”。

这里建议明确分层：

1. 状态静态属性负责描述状态身份。
2. 单位事件负责描述状态内部的时序窗口。

不应把所有控制都塞进单一布尔字段，也不应把所有状态身份都退化成 0 秒触发的事件。

更合理的分工是：

1. `Layer`、`PresentationMode`、`ControlsMovement`、`ControlsRotation` 这类内容，属于状态静态属性。
2. `何时允许移动取消`、`何时关闭下盘`、`何时恢复转向`、`何时允许下一技能`，属于单位事件控制的时序门禁。

这样做的好处是：

1. 状态身份清晰，不会因为事件时序而变得难以理解。
2. 可打断窗口、输入窗口、控制限制窗口都能做到精确到时间点。
3. 很适合当前项目已经存在的多轨时间线模型。

这里还要补一条实现原则：

1. 单位事件不要直接留下裸开关状态。
2. 门禁应按“可回收的作用域”管理。
3. 无论状态自然结束还是被打断退出，都必须统一清理该状态施加的门禁影响。

否则后续很容易出现“状态提前退出，但禁移动/禁转向没有恢复”的脏状态问题。

### 5.7 当前阶段不单独引入“推进策略系统”

经过充分讨论，当前阶段不建议把“时间线推进策略”做成一套独立基础系统。

原因是：

1. 现有 `State` 更适合通过“状态迁移”解决副作用问题。
2. 当前项目目标是尽量小改，不宜再额外增加一套与状态机并行的推进模式抽象。
3. 很多现阶段问题，都可以通过“动作改变共享事实 -> 其他层自然切到安全状态”来解决。

因此，当前阶段的主张是：

1. 优先用规则自然导出的状态迁移解决层间影响。
2. 不先引入 `Normal`、`Freeze`、`Redirect` 一类独立推进策略枚举作为基础设计。

但要记录一个未来边界：

1. 如果后续出现命中停顿、极短暂冻结、处决演出、保留状态身份但临时停时间线等需求，项目未来仍可能补入“推进方式控制”这一层抽象。

这属于后续高级扩展，不属于当前阶段的最小实现目标。

## 6. 第一阶段数据结构定稿

这一节不再只是“建议方向”，而是第一阶段准备实际落地的数据契约。

目标只有三个：

1. 让每个 `State` 的身份、时序、打断语义彻底分开。
2. 让分层状态机在现有配置和运行时骨架上可平滑演进。
3. 让后续编辑器、运行时、迁移工具都围绕同一份数据语义工作。

### 6.1 第一阶段需要新增的核心枚举

第一阶段建议引入以下枚举：

1. `StateLayerType`
2. `StatePresentationMode`
3. `StateAnimationSlot`
4. `LocomotionImpactMode`
5. `GateControlType`
6. `GateValueMode`
7. `StateTransitionPolicy`

推荐语义如下。

`StateLayerType`：

1. `None`
2. `Locomotion`
3. `Action`

第一阶段只开放这两条主层，后续如果要扩展上层逻辑层，再往后加，不在一期透支设计。

`StatePresentationMode`：

1. `None`
2. `FullBodyOverride`
3. `UpperBodyOverlay`
4. `AdditiveOverlay`

它只描述最终表现混合方式，不直接决定状态逻辑切换。

`StateAnimationSlot`：

1. `None`
2. `Locomotion`
3. `Action`
4. `UpperBody`
5. `Additive`

第一阶段逻辑层只用 `Locomotion` 和 `Action`，但动画槽位先把未来出口预留好。

`LocomotionImpactMode`：

1. `None`
2. `KeepCurrentFacts`
3. `LockMoveInput`
4. `LockLocomotionState`
5. `ForceSafeState`

它描述当前状态对底盘共享事实的影响方式，而不是直接写底盘目标状态。

`GateControlType`：

1. `MoveInput`
2. `LocomotionDrive`
3. `RotationInput`
4. `Dash`
5. `SkillCancel`
6. `NextSkill`
7. `RootMotion`

第一阶段不需要一次做全，但枚举的语义要先统一，避免后面门禁事件各写各的。

`GateValueMode`：

1. `Enable`
2. `Disable`
3. `Override`

用于门禁事件表达“开启、关闭、强制覆盖”的区别。

`StateTransitionPolicy`：

1. `SameLayerOnly`
2. `AllowWhitelistedCrossLayer`
3. `ForceGlobal`

它不要求外部每次手填，但运行时和编辑器需要围绕这个语义做校验。

### 6.2 `StateConfig` 的第一阶段定稿字段

当前 [UnitConfig.cs](Assets/SkillEditor/Runtime/Config/Unit/UnitConfig.cs) 中的 `StateConfig` 是第一阶段的主改造点。

推荐定稿结构如下：

1. 现有保留字段：
2. `string StateId`
3. `string StateName`
4. `string AnimationClipPath`
5. `string DefaultNextStateId`
6. `StateTimelineConfig Timeline`
7. `TagContainer Tags`
8. 新增身份字段：
9. `StateLayerType Layer`
10. `StatePresentationMode PresentationMode`
11. `StateAnimationSlot PrimaryAnimationSlot`
12. 新增控制语义字段：
13. `bool ControlsMovement`
14. `bool ControlsRotation`
15. `bool BlocksLocomotionAnimation`
16. `LocomotionImpactMode LocomotionImpactMode`
17. 新增层内切换辅助字段：
18. `bool IsLayerDefaultState`
19. `bool IsActionReleaseState`
20. `string SafeFallbackStateId`

各字段语义要钉死如下：

1. `Layer`：这个状态在逻辑上属于哪一层。这是分层状态机里最关键的身份字段。
2. `PresentationMode`：这个状态如何参与最终表现混合。
3. `PrimaryAnimationSlot`：这个状态默认输出到哪个槽位，不等于只能输出到这个槽位。
4. `ControlsMovement`：这个状态是否声明自己接管位移控制权。
5. `ControlsRotation`：这个状态是否声明自己接管转向控制权。
6. `BlocksLocomotionAnimation`：这个状态是否在视觉上压住底盘动画输出。
7. `LocomotionImpactMode`：这个状态如何影响底盘共享事实，不允许借此直接指定底盘跳到哪个具体状态。
8. `IsLayerDefaultState`：是否可作为某一层的默认回落态。
9. `IsActionReleaseState`：是否是 Action 层的统一“释放占用态/空态”。第一阶段正式采用这条路线，让 move cancel 一类语义稳定落到明确状态，而不是直接跳 `Run`，也不是额外走第二套特殊退出请求。
10. `SafeFallbackStateId`：当当前状态自然结束或规则失效时，优先建议切回的同层安全状态。它是辅助建议，不是强制跨层跳转。

这里要特别强调两条：

1. `DefaultNextStateId` 保留，继续承担“状态自然结束后进入下一状态”的职责。
2. `SafeFallbackStateId` 是新增的“异常/规则失效/释放占用时的同层安全回落建议”，它不替代 `DefaultNextStateId`。

### 6.3 `StateTimelineConfig` 的第一阶段定稿职责

当前 [StateRuntimeConfig.cs](Assets/SkillEditor/Runtime/Config/State/StateRuntimeConfig.cs) 里的 `StateTimelineConfig` 已经很接近可用结构，第一阶段不需要推翻，只需要钉死职责边界。

它继续保留：

1. `float Duration`
2. `TimelineAnimationConfig Animation`
3. `List<TimelineTrackConfig> Tracks`
4. `List<StateInterruptTrackConfig> InterruptTracks`
5. `List<StateInterruptConfig> Interrupts`

其中职责要定为：

1. `Animation`：只负责该状态自身的动画播放参数。
2. `Tracks`：承载命中盒、子弹、事件等时序内容。
3. `InterruptTracks`：承载该状态的打断窗口与打断目标。
4. `Interrupts`：仅保留为旧格式兼容入口，新配置以后优先使用 `InterruptTracks`。

第一阶段不新增第二套“门禁轨道”容器。

原因是当前 [TimelineTrackConfig.cs](Assets/SkillEditor/Runtime/Config/State/TimelineTrackConfig.cs) 和 [TimelineEventConfig.cs](Assets/SkillEditor/Runtime/Config/State/TimelineEvent/TimelineEventConfig.cs) 已经具备承载时序事件的能力。

门禁控制应该作为一种新的 `TimelineEventData` 类型进入现有事件体系，而不是再发明一条平行轨道。

### 6.4 `TimelineTrackConfig` 与事件体系的定稿职责

当前 `TimelineTrackConfig` 已经承载：

1. `HitBoxes`
2. `Bullets`
3. `MetaSkillEvents`

第一阶段不改它的骨架，但要定清楚事件体系的未来分工：

1. 表现事件：例如特效、镜头、音效、吸附、重力、受力等。
2. 控制门禁事件：例如禁移动输入、禁下盘驱动、开放下一技能取消、开放 dash cancel 等。

因此第一阶段建议新增一种新的 `TimelineEventData` 分支，例如：

1. `StateGateControl_TimelineEventData`

它推荐至少包含：

1. `GateControlType GateType`
2. `GateValueMode ValueMode`
3. `bool Value`
4. `string SourceToken`
5. 可选 `string Notes`

语义如下：

1. `GateType`：这个事件控制哪种门禁。
2. `ValueMode`：是开启、关闭，还是强制覆盖。
3. `Value`：门禁目标值。
4. `SourceToken`：用于状态退出时识别并清理该状态产生的门禁作用域。

这样，门禁可以复用当前时间线事件生命周期，而不是在状态外面裸写布尔开关。

### 6.5 `StateInterruptConfig` 的第一阶段定稿语义

当前 `StateInterruptConfig` 的结构本身已经够用，但它的语义必须在分层后重新钉死。

它继续保留：

1. `TargetStateId`
2. `TriggerTime`
3. `Duration`
4. `ExecuteTime`
5. `SortOrder`
6. `Conditions`

第一阶段新增或补充的推荐字段是：

1. `StateTransitionPolicy TransitionPolicy`

语义如下：

1. `TargetStateId`：默认应指向同层目标状态。
2. `TransitionPolicy`：定义这个打断配置在层校验时的合法范围。
3. 对于“这次中断的目的不是跳到另一个动作，而是结束当前动作占用”的情况，第一阶段统一要求把 `TargetStateId` 指向 Action 层的统一释放态，而不是走第二套特殊退出语义。

第一阶段要在运行时与编辑器里固定下面三条规则：

1. 普通打断轨默认只能命中同层目标。
2. `MoveInput` 命中 Action Recovery 时，不允许直接跳 `Run`，必须落到 Action 同层统一释放态。
3. 跨层强制切换只能由白名单全局状态触发，例如 `HitReact`、`Knockdown`、`Death`。

### 6.6 `StateTransitionRequest` 的第一阶段定稿结构

当前 [StateController.cs](Assets/SkillEditor/Runtime/Runtime/State/StateController.cs) 中的 `StateTransitionRequest` 只服务单活动态，但它不需要变成一个很重的对象。

推荐定稿字段如下：

1. 现有保留字段：
2. `StateTransitionRequestType RequestType`
3. `string SourceStateId`
4. `string TargetStateId`
5. `StateInterruptConfig InterruptConfig`
6. `bool IgnoreInterruptRules`
7. `float RequestedStartTime`
8. `SkillTransitionContext SkillTransitionContext`
9. 新增字段：
10. `StateLayerType? SourceLayerHint`
11. `bool IsGlobalForcedTransition`

语义如下：

1. `SourceLayerHint`：给运行时一个更便宜的层定位提示，避免每次都从旧兼容语义倒推。
2. `IsGlobalForcedTransition`：表达这是白名单式全局强制切换，允许突破普通同层限制。

这里的关键原则是：

1. 层归属最终仍然以目标 `StateConfig.Layer` 为准。
2. `SourceLayerHint` 只是优化和兼容字段，不是外部自由指定层归属的入口。
3. 第一阶段不保留“释放 Action 层占用”的第二套请求语义；需要退出占用时，统一切到 Action 层释放态。

### 6.7 第一阶段运行时结构定稿

第一阶段不拆多个 `StateController`，而是在一个控制器内部持有多层活动态。

推荐运行时结构如下：

1. `Dictionary<StateLayerType, StateLayerRuntime> _layerRuntimes`
2. `Dictionary<string, StateConfig> _statesById`
3. `StateSharedControlContext _sharedControlContext`
4. `StateGateAggregator _gateAggregator`

其中 `StateLayerRuntime` 推荐包含：

1. `StateLayerType LayerType`
2. `string DefaultStateId`
3. `ActiveStateRuntime Current`
4. `StateTransitionRequest PendingRequest`

其中 `StateSharedControlContext` 推荐包含：

1. `bool AllowMoveInput`
2. `bool AllowLocomotionDrive`
3. `bool AllowRotationInput`
4. `bool AllowDash`
5. `bool AllowNextSkill`
6. `bool UseRootMotion`

其中 `StateGateAggregator` 推荐职责是：

1. 聚合同帧所有生效中的门禁事件。
2. 按来源状态或事件 token 记录作用域。
3. 在状态自然结束或中断退出时统一清理该状态施加的控制影响。

第一阶段不要把这些运行时结构暴露成很多对外接口。

先让它们作为 `StateController` 内部结构稳定下来，再决定要不要向外暴露更多调试入口。

### 6.8 `CurrentStateConfig` 与兼容访问器的定稿规则

因为旧代码大量假设“当前只有一个状态”，所以第一阶段必须保留兼容访问规则。

定稿如下：

1. 如果 `Action` 层有活动状态，则 `CurrentStateConfig` 返回 `Action` 层当前状态。
2. 否则返回 `Locomotion` 层当前状态。
3. `CurrentStateId` 采用同样兼容语义。

同时新增明确访问器：

1. `GetCurrentState(StateLayerType layer)`
2. `GetCurrentStateId(StateLayerType layer)`
3. `GetStateElapsedTime(StateLayerType layer)`

这样旧链路不立刻被打断，新链路也不会继续依赖模糊语义。

### 6.9 第一阶段兼容迁移规则定稿

因为这次是在已有框架上改，所以兼容策略必须和数据结构一起定下来。

第一阶段建议固定以下迁移规则：

1. 旧状态如果没有 `Layer`，默认归为 `Locomotion`。
2. 技能 execute/recovery 所引用的状态，迁移后默认归为 `Action`。
3. 旧状态如果没有 `PresentationMode`，按 `Layer` 给默认值：
4. `Locomotion -> FullBodyOverride`
5. `Action -> FullBodyOverride`
6. 旧状态如果没有 `PrimaryAnimationSlot`，按 `Layer` 推导：
7. `Locomotion -> Locomotion`
8. `Action -> Action`
9. 旧状态如果没有 `ControlsMovement/ControlsRotation`，默认都为 `false`。
10. 旧打断轨如果没有 `TransitionPolicy`，默认按 `SameLayerOnly` 处理。
11. 旧 `Interrupts` 平铺列表在加载时自动并入默认打断轨视图，但编辑器新保存优先写 `InterruptTracks`。

这里最重要的一条是：

1. 不允许因为兼容旧数据，就在新系统里默许跨层打断成为常态。

兼容策略的目标是“旧配置还能跑”，不是“保留旧设计里所有模糊语义”。

### 6.10 第一阶段必须遵守的结构边界

为了避免返工，第一阶段的数据结构必须明确拒绝以下做法：

1. 不新增第二套平行状态时间线系统。
2. 不把 `UpperBody`、`Additive` 直接做成完整逻辑层。
3. 不允许 `Action` 打断轨默认直接跳 `Run` 一类 `Locomotion` 状态。
4. 不把所有门禁直接写成 `StateConfig` 静态布尔值。
5. 不让单位事件直接留下无法随状态退出而回收的裸开关。

这一组边界，和上面的字段本身一样重要。

## 7. `StateController` 的演化方式

### 7.1 不改入口，只改内核

当前 `StateController` 对外已经有一套可工作的入口：

1. `Tick`
2. `TryChangeState`
3. `ForceChangeState`
4. `CurrentStateId`
5. `CurrentStateConfig`

第一阶段最稳的做法不是推翻这些接口，而是：

1. 尽量保留现有入口。
2. 在内部把“唯一活动态”改成“分层活动态集合”。

这能最大限度减小对 [SkillRuntime.cs](Assets/SkillEditor/Runtime/Runtime/Skill/SkillRuntime.cs)、[SkillPlayerController.cs](Assets/SkillEditor/Runtime/Runtime/Skill/SkillPlayerController.cs) 和 Buff 链路的冲击。

### 7.2 `CurrentStateConfig` 保留兼容语义

很多旧代码可能仍然只会问：当前状态是什么。

第一阶段建议保留兼容语义：

1. 如果 `Action` 层当前有活动状态，则 `CurrentStateConfig` 返回 `Action` 层状态。
2. 否则返回 `Locomotion` 层状态。

同时新增更明确的访问器：

1. `GetCurrentState(StateLayerType layer)`
2. `GetCurrentStateId(StateLayerType layer)`
3. `GetStateElapsedTime(StateLayerType layer)`

这样既不打烂旧逻辑，也为新逻辑提供正确入口。

### 7.3 `Tick` 改成“分层推进 + 分层协调”

当前 `Tick` 逻辑基本是：

1. 保证有默认状态
2. 推进 `_activeState`
3. 同步动画
4. 评估中断
5. 处理自然结束

分层后建议变成：

1. 保证 `Locomotion` 层有默认状态。
2. 推进 `Locomotion` 层。
3. 推进 `Action` 层。
4. 分别评估各层中断。
5. 先在各层内部完成各自的状态切换。
6. 汇总 `Action` 当前状态带来的共享事实影响，例如是否锁移动、是否锁转向。
7. 让其他层根据这些事实自然迁移到安全状态或维持当前状态。
8. 汇总动画请求并交给动画控制器。

这里最重要的是：

1. 各层先独立推进。
2. 打断轨优先在层内闭环解决，不默认跨层跳目标状态。
3. 层间影响优先通过规则自然导出状态迁移。
3. 少数全局强制状态才由总控制器统一裁决。

不要在某一层的 `Tick` 内部直接硬编码另一层的表现处理。

### 7.4 技能驱动状态只进入 `Action` 层

当前技能主线通过 `SkillTransitionContext` 与 `StateController` 对接。

这条链路第一阶段不应该乱动。

建议明确规定：

1. 技能 execute/recovery 注入的状态，一律属于 `Action` 层。
2. `SkillStateChanged` 事件目前只从 `Action` 层发回技能系统。
3. `Locomotion` 层暂时不参与技能状态通知。

这样可以确保状态分层改造不会立刻波及整个技能执行架构。

## 8. 动画表现层如何配合

### 8.1 当前阶段不要急着做完整动画图

当前阶段主要解决动画播放与切换，所以目标不是一步到位做出最终 `AnimationSlotController` 全家桶。

第一阶段只需要做到：

1. `Locomotion` 层可以持续产出底盘状态动画。
2. `Action` 层可以产出高优先级动作动画。
3. 动画控制器能根据覆盖规则决定当前可见输出。

### 8.2 先从“状态动画请求”演化成“分层动画请求”

当前 `ICharacterAnimationController` 还是围绕：

1. `PlayStateAnimation`
2. `SyncStateAnimation`
3. `StopStateAnimation`

第一阶段可以先不彻底重做接口，但内部语义要开始变化：

1. 不是只有一个“当前状态动画”。
2. 而是按层/槽位消费状态输出。

建议第一阶段先在内部引入一个请求模型，例如：

1. `StateAnimationRequest`

它至少包含：

1. 来源状态层
2. 目标动画槽
3. 动画片段路径
4. 混合参数
5. 起始时间
6. 覆盖模式
7. 是否需要持续时间同步

然后 `StateController` 在每帧推进完以后生成这些请求，由动画控制器统一消费。

### 8.3 第一阶段的表现规则

第一阶段建议只实现下面三条规则：

1. `Locomotion` 状态始终驱动 `Locomotion` 槽。
2. `Action` 状态可以根据 `PresentationMode` 写入 `Action` 槽。
3. 如果 `Action` 状态是 `FullBodyOverride`，则视觉上压住 `Locomotion` 槽；否则两者共存。

同时要明确一条补充规则：

1. `FullBodyOverride` 只描述最终可见表现，不等于“`Locomotion` 必然继续完整推进原状态时间线”。
2. `Locomotion` 当前是否仍是 `Run`，应由底盘事实和自身状态规则决定。
3. 如果 `Action` 锁移动导致 `Run` 条件失效，`Locomotion` 应自然切到安全状态，而不是继续完整推进 `Run` 时间线。

这已经足够支撑：

1. 原地或移动中攻击。
2. 技能动作接管表现。
3. 动作结束后自动恢复底盘动画。

## 9. 为什么这套改法是“尽量小的正确改法”

这套方案的价值，不在于它概念多，而在于它尽量避免了三种失控。

### 9.1 不拆多控制器，避免架构横向爆炸

如果现在就拆多个平级控制器，会立刻遇到：

1. 输入归谁收。
2. 命中受击归谁判。
3. 技能状态回调归谁发。
4. 多控制器之间谁是主调度。

这对当前项目来说风险太高。

保留一个 `StateController`，只是在内核里维护多层活动态，是更稳的路线。

### 9.2 不把所有动画槽都立刻做成状态层，避免数据复杂度失控

`UpperBody` 和 `Additive` 确实很重要，但当前阶段不需要让它们变成完整状态层。

先把它们定义成动画槽位或表现模式预留，就能避免：

1. 状态数暴涨。
2. 中断规则暴涨。
3. 时间线配置暴涨。

### 9.3 不推翻现有技能和状态 runtime 主线

当前技能状态主线、`SkillTransitionContext`、`StateTimelineExecutionRuntime` 都已经能跑。

这次改造不应该把这些重写。

应该改的是：

1. 状态归属层。
2. 控制器内部持有多个活动态。
3. 动画请求的分层输出。

也就是说，改“状态机骨架”，不改“时间线执行内脏”。

## 10. 推荐落地顺序

### 阶段 1：补齐数据归属

先改配置层，不动复杂运行时逻辑。

需要做：

1. 给 `StateConfig` 增加 `Layer`。
2. 给 `StateConfig` 增加 `PresentationMode`。
3. 给现有状态补齐初始层归属。
4. 给关键 `Action` 状态补齐移动/转向影响声明。

目标：让每个状态先有明确的层语义。

### 阶段 2：把 `StateController` 改成单控制器多层运行时

需要做：

1. 去掉唯一 `_activeState` 的中心结构。
2. 引入多层活动态容器。
3. 让 `Locomotion` 和 `Action` 各自独立推进和中断评估。
4. 让层间影响先通过共享事实和自然状态迁移落地。
5. 保留现有兼容入口。

目标：逻辑上实现“多轨状态机”。

### 阶段 3：把状态动画播放改成分层输出

需要做：

1. 从状态层生成动画请求。
2. 动画控制器按槽位消费请求。
3. 支持 `FullBodyOverride` 对底盘槽位的视觉压制。

目标：先把动画分层播放真正跑起来。

### 阶段 4：接 RootMotion 和移动/转向接管策略

需要做：

1. 让状态声明是否控制移动。
2. 让状态声明是否控制转向。
3. 把动作层和运动层的所有权规则接到移动系统。

目标：把“动画分层正确”推进到“手感正确”。

### 阶段 5：未来高级边界扩展

这一阶段不进入当前实现，但建议在设计上留档。

未来可能补入：

1. 命中停顿与局部冻结
2. 保留状态身份但临时停止时间线推进
3. 处决、演出、Cinematic 控制
4. 更细粒度的轨道级推进控制

这些需求出现时，项目才有必要正式引入独立的“时间线推进方式控制”抽象。

## 11. 当前方案结论

结合当前项目结构和 `AsiActionEditor` 的参考，最合适的分层状态机方案不是：

1. 拆多个平级 StateController。
2. 每个层都做成一个独立大系统。
3. 一上来就把 UpperBody、Additive 也做成完整逻辑状态层。

而是：

1. 继续保留一个 `StateController`。
2. 把它从“单活动态”升级成“多层活动态集合”。
3. 第一阶段只做 `Locomotion` 和 `Action` 两条状态层。
4. `UpperBody` 和 `Additive` 先作为动画输出槽和表现模式预留。
5. `Action` 默认不直接跨层硬改其他层状态，而是通过共享事实间接影响其他层自然迁移。
6. 少数全局强制状态由总控制器统一跨层裁决。
7. 技能状态主线继续只走 `Action` 层，最大化复用现有 runtime。

这是当前项目最稳、最小、也最符合高级 ARPG 3C 方向的改法。

## 12. 下一步要进入实现前，必须先钉死的四个点

进入代码前，我建议先把下面三件事正式定死。

### 12.1 `StateConfig` 第一阶段到底要加哪几个字段

最少建议先定：

1. `Layer`
2. `PresentationMode`
3. `ControlsMovement`
4. `ControlsRotation`

### 12.2 `Locomotion` 层默认状态集和默认跳转边界

也就是先定义：

1. `Idle / Walk / Run / Sprint / Jump / Falling / Land` 这批状态如何组织。
2. 哪些是底盘内部自然切换。
3. 哪些必须由外部输入或运动结果驱动。

### 12.3 `Action` 对 `Locomotion` 的三种表现关系

建议明确只保留三类：

1. 全身覆盖
2. 上半身覆盖
3. 叠加

只要这三类先定清楚，后面动画请求模型和槽位控制器就不会乱。

### 12.4 `Action` 如何通过规则影响 `Locomotion`

这一点现在也必须定死。

最少要明确：

1. 哪些 `Action` 会锁移动。
2. 哪些 `Action` 会锁转向。
3. 当 `Run`、`Walk` 等状态条件失效时，`Locomotion` 应该自然回落到哪个安全状态。
4. 哪些全局强制状态允许总控制器直接做跨层裁决。

这部分一旦定清楚，项目就能在不引入额外推进策略系统的前提下，稳定解决时间线副作用问题。

## 13. 未来边界记录

虽然当前阶段不把“推进策略”做成正式基础设计，但这个边界值得记录下来，避免未来重复争论。

1. 时间线推进方式控制

但这属于后续高级能力，不属于当前阶段的最小落地要求。
