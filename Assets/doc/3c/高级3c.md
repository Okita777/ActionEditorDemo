# 高级3C改造设计

## 1. 目标

本文档用于收敛当前技能编辑器在 3C 方向上的核心改造计划。目标不是做一套“能播动画”的技能系统，而是做一套能够支撑高规格 ARPG 角色表现的运行时框架与编辑器。

本轮讨论聚焦三个问题：

1. ActionBridge 的历史设计遗留与职责失真。
2. 高级动画系统所需的分层状态机与动画槽位模型。
3. 移动系统、KCC、RootMotion 与技能动作之间的协作关系。

最终目标是形成一套具备以下特征的 3C 基础设施：

1. 逻辑规则清晰，技能、移动、受击、下落等行为之间不存在职责混叠。
2. 动画表现可分层、可混合、可覆盖，能支持移动中攻击、上半身动作、受击叠加、镜头联动等高级表现。
3. 位移和转向可被精细控制，RootMotion 既不失控，也不被完全废掉。
4. 编辑器侧可以稳定配置行为规则、动画槽位、移动策略和过渡规则，而不是继续堆特例。

## 2. 问题本源

### 2.1 当前 ActionBridge 的根问题

当前 [ICharacterActionBridge.cs](Assets/SkillEditor/Runtime/Interfaces/ICharacterActionBridge.cs) 和 [SkillCharacterActionBridge.cs](Assets/SkillEditor/Runtime/Runtime/Skill/SkillCharacterActionBridge.cs) 的主要问题不是“代码写得旧”，而是职责边界已经失真：

1. 它同时承担了状态动画播放、MetaSkill 动画播放、中断窗口缓存、组件扫描、Animancer 注入、施法态门控等多种职责。
2. 接口表面上支持 State 动画与 MetaSkill 动画两套入口，但当前真正稳定的调用主线只有 State 动画。
3. `SyncMetaSkillAnimation` 和 `SyncMetaSkillRecoveryAnimation` 实际上已经处于空壳状态。
4. `BeginInterruptWindow` / `UpdateInterruptWindow` / `EndInterruptWindow` 把战斗规则侧状态塞进动画桥本体，不属于纯表现层职责。
5. `IsCasting` 把“是否进入技能态”粗暴实现成动画总开关，直接阻断 State 动画，这不适合高级动作表现。
6. 当前桥只维护一个 `_activeAnimationState`，天然只能表达单轨动画。

结论：

ActionBridge 现在不是“角色动画桥”，而是“历史上所有和角色表现有关的逻辑兜底容器”。如果不先收缩职责，后续分层动画、移动策略、RootMotion 策略都会继续互相污染。

### 2.2 当前状态机的根问题

当前 [StateController.cs](Assets/SkillEditor/Runtime/Runtime/State/StateController.cs) 同时承担了：

1. 主逻辑状态推进。
2. 技能状态通知。
3. 动画播放入口。
4. 动画时间同步。
5. 中断窗口求值。

而这套模型默认前提是：

1. 一个角色同一时刻只有一个主状态。
2. 一个主状态只对应一个播放动画。
3. 状态变化就意味着动画切换。

这在简单技能系统里能工作，但无法表达以下高级动作需求：

1. 跑动中出招。
2. 上半身攻击，下半身继续移动。
3. 受击叠加而不打断底盘。
4. 动作期允许有限移动或有限转向。
5. 空中动作与下落姿态并存。

结论：

不是“状态没用了”，而是“单层唯一状态机”已经不足以表达高级 ARPG 的运动与动作关系。

### 2.3 当前移动系统的根问题

当前移动实现位于：

1. [CustomCharacterController.cs](Assets/Scripts/character_motion/CustomCharacterController.cs)
2. [RootMotionSource.cs](Assets/Scripts/character_motion/RootMotionSource.cs)
3. [InputMotionSource.cs](Assets/Scripts/character_motion/InputMotionSource.cs)
4. [CharacterVelocity.cs](Assets/Scripts/character_motion/CharacterVelocity.cs)
5. [CharacterRotation.cs](Assets/Scripts/character_motion/CharacterRotation.cs)

这套结构的优点是明确的：

1. 最终执行层是 KCC，碰撞和地形行为统一。
2. 输入、AI、RootMotion、外力被抽象成统一 MotionSource。
3. RootMotion 不是直接推 Transform，而是先提取 delta，再交给控制器统一执行。

但当前仍有几个关键不足：

1. 输入位移与 RootMotion 位移主要是叠加关系，缺少“谁拥有平移权”的裁决。
2. 输入转向与 RootMotion 转向也可能同时生效，缺少“谁拥有转向权”的裁决。
3. RootMotion 还不支持按轴、按动作期、按相位、按权重筛选。
4. 普通 locomotion 目前更偏代码速度驱动，若动画步频和速度不严格匹配，仍然会出现滑步。

结论：

当前移动底层运输层方向是正确的，不应推翻；需要补的是“运动所有权”和“动作期运动策略”。

## 3. 总体设计原则

面向高规格 ARPG 3C，本项目后续改造遵循以下原则：

1. 逻辑状态、移动控制、动画表现三者解耦。
2. 状态不再直接等于唯一播放动画。
3. 普通 locomotion 以代码驱动为主，关键动作期选择性启用 RootMotion。
4. 动画播放不再由单个 `_activeAnimationState` 承载，而是由多个槽位协同。
5. 技能是否可释放，不只由 ActionState 决定，还要经过 locomotion / posture 规则层 gate。
6. 编辑器层要能显式配置：
	1. 动画槽位。
	2. 动作覆盖规则。
	3. 移动策略。
	4. 转向策略。
	5. RootMotion 使用策略。

## 4. 目标架构

### 4.1 三层职责拆分

后续角色运行时拆成三层：

1. 规则层
2. 运动层
3. 表现层

#### 4.1.1 规则层

负责回答：角色当前允许做什么。

包括：

1. LocomotionStateController
2. ActionStateController
3. 技能释放 gate
4. 中断与取消规则

#### 4.1.2 运动层

负责回答：角色这一帧如何移动、如何转向。

包括：

1. KCC 执行器
2. MotionSource 汇总
3. 新的 MovementController 作为策略裁判
4. RootMotion 使用模式切换

#### 4.1.3 表现层

负责回答：角色各个槽位现在播什么、怎么混、谁覆盖谁。

包括：

1. AnimationSlotController
2. Locomotion 槽
3. Action 槽
4. Additive 槽
5. 可选 UpperBody 槽

### 4.2 双状态线模型

后续不再依赖“唯一主状态”表达全部角色行为，而是采用至少两条正交状态线：

1. Locomotion 状态线
2. Action 状态线

#### 4.2.1 Locomotion 状态线

负责底盘、机动姿态与动作资格。

典型状态：

1. Idle
2. Walk
3. Run
4. Sprint
5. Jump
6. Falling
7. Land

这条状态线主要决定：

1. 底盘动画。
2. 是否接地。
3. 是否允许地面技能。
4. 是否允许空中技能。
5. 是否允许移动和转向。

#### 4.2.2 Action 状态线

负责技能、闪避、受击等高优先级动作。

典型状态：

1. None
2. Skill1_1
3. Skill1_2
4. Dodge
5. Hit
6. Knockdown

这条状态线主要决定：

1. 当前执行哪段技能或动作。
2. 当前连段窗口。
3. 当前取消/中断规则。
4. 当前移动策略与转向策略。
5. 当前动作对应哪个动画槽位。

### 4.3 动画槽位模型

目标槽位如下：

1. Locomotion 槽
2. Action 槽
3. Additive 槽
4. 可选 UpperBody 槽

#### 4.3.1 Locomotion 槽

负责基础移动表现。

典型内容：

1. Idle
2. Walk
3. Run
4. Sprint
5. Jump / Fall / Land

#### 4.3.2 Action 槽

负责高优先级主体动作。

典型内容：

1. 技能 execute / recovery
2. Dodge
3. 受击
4. 处决

#### 4.3.3 Additive 槽

负责附加层表现。

典型内容：

1. 轻受击抖动
2. 武器后坐
3. 呼吸姿态修正
4. 轻微镜头联动附加动作

#### 4.3.4 UpperBody 槽

用于移动中上半身独立动作。

典型内容：

1. 跑动中挥砍
2. 移动中施法
3. 奔跑中射击
4. 上半身瞄准

## 5. ActionBridge 改造设计

### 5.1 目标

把 ActionBridge 从“表现垃圾桶”收缩成“表现请求入口”。

### 5.2 现有接口处理方向

#### 5.2.1 判定为历史遗留、应逐步下线的接口

1. `PlayMetaSkillAnimation`
2. `SyncMetaSkillAnimation`
3. `PlayMetaSkillRecoveryAnimation`
4. `SyncMetaSkillRecoveryAnimation`
5. `StopMetaSkillAnimation`
6. `BeginInterruptWindow`
7. `UpdateInterruptWindow`
8. `EndInterruptWindow`

原因：

1. MetaSkill 动画主线当前不构成稳定真实调用链。
2. 中断窗口属于规则/调试/可视化侧，不应继续挂在动画桥上。

#### 5.2.2 临时保留、但后续必须重构语义的接口

1. `EnterCastingState`
2. `ExitCastingState`
3. `PlayStateAnimation`
4. `SyncStateAnimation`
5. `StopStateAnimation`

这些接口短期仍可作为兼容层存在，但最终应改为“请求式接口”，而不是命令式播放接口。

### 5.3 新的表现层接口方向

后续应收敛为类似以下语义：

1. 提交动画请求
2. 更新动画请求
3. 释放动画请求
4. 查询槽位状态

请求应至少包含：

1. 槽位类型
2. 动画资源或状态 Id
3. 淡入时长
4. 起播时间
5. 是否允许自然推进
6. 是否允许覆盖 / 被覆盖
7. 优先级
8. BodyMask
9. RootMotion 策略
10. 请求来源 Id

## 6. 分层状态机设计

### 6.1 LocomotionStateController

LocomotionStateController 用于维护角色底盘姿态，不负责技能逻辑。

职责：

1. 根据接地、速度、输入、垂直速度决定底盘状态。
2. 提供动作资格 gate，例如 Falling 禁止地面技能。
3. 提供底盘动画请求给 Locomotion 槽。

### 6.2 ActionStateController

ActionStateController 用于维护技能、闪避、受击等动作主线。

职责：

1. 推进技能 execute / recovery。
2. 处理动作中断、取消、连段与窗口。
3. 提供 Action / UpperBody 槽动画请求。
4. 提供动作期移动策略与转向策略。

### 6.3 规则 gate 顺序

后续技能释放应按以下顺序检查：

1. 当前 locomotion 状态是否允许该技能类别。
2. 当前 action 状态是否允许进入新动作。
3. 资源、冷却、标签等系统规则是否通过。
4. 若通过，再进入对应 ActionState。

示例：

1. `Falling` + 地面技能 => 直接拒绝。
2. `Run` + 可移动中释放技能 => 允许。
3. `Hit` + 非霸体技能 => 直接拒绝。

## 7. 移动系统与 RootMotion 设计

### 7.1 对当前 KCC 架构的结论

当前 KCC + MotionSource + RootMotionSource 方案不需要推翻。

它已经具备一个合理高级动作系统所需的基础执行层：

1. KCC 负责最终执行位移与旋转。
2. 输入、AI、RootMotion、外力是可组合来源。
3. RootMotion 由动画产生，但不直接支配 Transform。

后续要新增的是 MovementController，而不是替代 KCC。

### 7.2 MovementController 的职责

MovementController 不是新的底层位移执行器，而是运动策略裁判。

它负责决定：

1. 当前是否允许输入位移。
2. 当前是否允许输入转向。
3. 当前是否允许 RootMotion 位移。
4. 当前是否允许 RootMotion 转向。
5. 当前哪一方拥有平移权。
6. 当前哪一方拥有转向权。
7. 当前是否允许重力。

### 7.3 建议的移动模式

建议 MovementController 至少支持以下模式：

1. InputOnly
2. RootOnly
3. Hybrid
4. Locked
5. RootRotationOnly

#### 7.3.1 InputOnly

1. 位移和转向主要由输入驱动。
2. RootMotion 仅用于表现，不主导真实运动。
3. 适用于日常 locomotion。

#### 7.3.2 RootOnly

1. 位移和转向主要由动画 delta 决定。
2. 输入只作为触发动作的条件。
3. 适用于突刺、翻滚、强演出动作。

#### 7.3.3 Hybrid

1. 输入与 RootMotion 共同生效。
2. 需要显式决定平移和转向的 ownership。
3. 适用于跑动中上半身攻击、有限移动技能。

#### 7.3.4 Locked

1. 输入位移和输入转向关闭。
2. 可选择只保留重力或只保留 RootMotion。
3. 适用于强硬直或站桩蓄力。

#### 7.3.5 RootRotationOnly

1. 平移由输入或代码控制。
2. 转向由动画根旋转主导。
3. 适用于转身斩、预摆拧身动作。

### 7.4 RootMotion 使用原则

#### 7.4.1 适合使用 RootMotion 的动作

1. 突刺
2. 翻滚
3. 前踏步挥砍
4. 强前冲技能
5. 受击后退
6. 处决

这些动作重心变化大、位移曲线重要、接触感要求高，应优先允许 RootMotion 参与真实运动。

#### 7.4.2 不适合主要依赖 RootMotion 的场景

1. 常规走跑冲刺
2. 日常转向
3. 空中下落
4. 空中修正
5. 频繁调参的基础机动

这些场景更适合代码驱动，再用动画跟随表现。

### 7.5 RootMotionSource 的后续增强方向

当前 [RootMotionSource.cs](Assets/Scripts/character_motion/RootMotionSource.cs) 还应补充如下能力：

1. 仅提取 XZ，不提取 Y。
2. 仅提取旋转，不提取位移。
3. 单独控制前向/横向位移权重。
4. 动作期内按相位启用 RootMotion。
5. 对不同槽位或不同动作设置不同的 RootMotion 策略。

## 8. 典型例子

### 8.1 跑动中上半身攻击

目标：角色跑动中释放一个可移动攻击技能。

运行时状态：

1. LocomotionState = Run
2. ActionState = Skill1_1

动作策略：

1. 槽位 = UpperBody
2. MovePolicy = Hybrid
3. TurnPolicy = FaceMoveDirection 或 LimitedTurn
4. VelocityScale = 0.6 ~ 0.8
5. Locomotion 槽继续播放 run
6. UpperBody 槽播放 Skill1_1 上半身动作

结果：

1. 角色仍可移动。
2. 下半身保持跑动。
3. 上半身执行攻击。

### 8.2 下落中禁止地面技能

目标：角色处于 Falling 状态时，不能释放地面技能。

运行时状态：

1. LocomotionState = Falling
2. ActionState = None

规则：

1. Falling 不允许 GroundOnly 技能。
2. 技能输入到来时先过 locomotion gate。
3. 不允许则直接拒绝进入 ActionState。

结果：

1. 角色仍保持 Falling。
2. 不进入 Skill1_1。
3. 底盘继续播放 Fall 动画。

## 9. 实施计划

### 第一阶段：ActionBridge 收缩与职责澄清

目标：先把旧桥变成可控兼容层，不再继续堆新逻辑。

内容：

1. 明确 MetaSkill 动画接口为待下线路径。
2. 中断窗口状态从 ActionBridge 中迁出。
3. 保留 State 动画接口，但只作为兼容入口。
4. 停止继续围绕 `_activeAnimationState` 增加能力。

### 第二阶段：分层状态机落地

目标：把唯一 StateController 模型拆成两条状态线。

内容：

1. 引入 LocomotionStateController。
2. 现有 Skill/动作逻辑收敛为 ActionStateController。
3. 建立技能释放前的双重 gate：Locomotion + Action。
4. 让 `Run / Falling / Land` 从“总状态机状态”转为底盘状态语义。

### 第三阶段：动画槽位系统落地

目标：从单轨动画升级到多槽位协同。

内容：

1. 建立 Locomotion 槽。
2. 建立 Action 槽。
3. 引入 UpperBody 槽。
4. 后续引入 Additive 槽。
5. 动画播放从命令式改成请求式。

建议顺序：

1. 先做 Locomotion + Action 双槽。
2. 跑通移动中攻击。
3. 再引入 UpperBody。
4. 最后处理 Additive。

### 第四阶段：MovementController 与 RootMotion 策略落地

目标：运动系统不推翻现有 KCC 架构，而是在其上加入动作期策略。

内容：

1. MovementController 管理输入、RootMotion、重力开关和 ownership。
2. RootMotionSource 支持按轴筛选、按相位筛选。
3. 为技能状态增加 MovePolicy / TurnPolicy / RootMotionPolicy。
4. 跑通以下典型场景：
	1. 普通跑步
	2. 跑动中上半身攻击
	3. 站桩蓄力
	4. 翻滚 / 突刺
	5. 下落中禁止地面技能

## 10. 编辑器配置方向

为了让这套 3C 系统真正可用，编辑器后续需要显式暴露以下配置：

1. State 所属状态线
2. 动画槽位类型
3. BodyMask
4. MovePolicy
5. TurnPolicy
6. RootMotionPolicy
7. VelocityScale
8. 是否允许技能期间继续 locomotion
9. 是否允许下落态释放
10. 是否允许空中转向

不能继续把这些规则隐式塞在运行时分支里，否则编辑器无法承担高级调参职责。

## 11. 结论

本次改造不是“补几个动画接口”或“给 ActionBridge 多加几个 if”。

真正要做的是：

1. 把旧的 ActionBridge 收缩成表现层兼容入口。
2. 把唯一状态机升级成分层状态机。
3. 把单轨动画升级成多槽位动画系统。
4. 把当前 KCC + RootMotionSource 升级成具备 ownership 和动作期策略的高级运动系统。

只有这样，技能编辑器后续才能真正支持：

1. 丝滑的动画衔接。
2. 稳定的移动中出招。
3. 合理的下落 / 受击 / 闪避规则。
4. 高规格 ARPG 需要的角色控制与表现统一。
