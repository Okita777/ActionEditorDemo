# 分层状态机设计

## 1. 当前讨论目标

本文档先不直接讨论具体代码拆成几个 Controller，也不先决定最终类图。

当前阶段只回答两个问题：

1. 要做出接近 3A 级 ARPG 水准的 3C 动画系统，底层应该满足什么条件。
2. 如果当前阶段主要解决动画的播放和切换，为什么必须引入分层状态机。

这里的重点不是“把动画播出来”，而是搭一套后续能持续扩展的底层骨架。

---

## 2. 顶级 ARPG 动画系统真正要解决什么

很多动作系统一开始的问题，不是动画资源不够，而是运行时表达能力太弱。

所谓高规格 ARPG 的 3C 动画，核心不是某个单独技术点，而是下面这几件事要同时成立：

1. 玩家输入要快响应。
2. 动作切换要稳定可控。
3. 角色运动、转向、受击、技能、落地这些行为不能互相打架。
4. 动画层之间要能叠加、覆盖、抢占，而不是永远只有一条主轨。
5. 所有过渡必须可预测，而不是靠堆特例碰运气。

如果把目标再说得具体一点，一套真正优秀的 ARPG 动画框架通常必须满足以下特征。

### 2.1 可读性

玩家和敌人都必须能看懂当前动作发生了什么。

这意味着：

1. 起手、进行中、收招的姿态区分要明确。
2. 重攻击、轻攻击、闪避、受击、硬直、倒地要有清晰的形体语言。
3. 状态切换不能在视觉上显得突兀、脏、漂。

可读性不是美术问题，而是状态切换规则问题。

### 2.2 响应性

顶级 3C 最敏感的一点，不是动作是否真实，而是输入之后角色多久给出可信反馈。

这意味着：

1. 输入被接受的时机要稳定。
2. 动作可取消、可衔接、可缓存的规则要明确。
3. 不能出现“逻辑已经切了，动画还挂在旧状态上”的延迟感。

如果状态机和动画系统耦得过死，响应性一定会越来越差。

### 2.3 连续性

角色的行为不能像 PPT 一样一段一段断开。

这意味着：

1. 跑动可以自然切入攻击。
2. 攻击中允许有限移动时，底盘和动作不会互相抢控制权。
3. 空中动作、落地、追击、受击等行为能连续衔接。

连续性要求运行时同时表达多条行为线，而不是只有一个“当前主状态”。

### 2.4 所有权清晰

动画系统里最容易失控的，不是播放接口，而是“这一帧到底谁说了算”。

至少要分清：

1. 谁决定当前逻辑状态。
2. 谁决定当前移动和转向。
3. 谁决定当前播哪些动画槽位。
4. 谁可以打断谁，谁只能叠加谁。

如果这些所有权不清楚，系统一定会退化成大量特殊判断。

### 2.5 分层与覆盖

高规格 ARPG 的动画表现几乎不可能只靠一条动画轨完成。

至少会遇到这些情况：

1. 下半身继续跑，上半身出招。
2. 主动作继续播，同时叠加轻微受击或后坐。
3. 底盘保持移动姿态，但高优先级动作临时接管部分骨骼。
4. 同一个动作状态下，可能还要叠加瞄准、表情、附加抖动。

这要求状态机不是单层唯一状态，而是能够驱动多个动画层的协作。

### 2.6 确定性过渡

顶级动作手感，底层一定有非常强的过渡确定性。

也就是：

1. 为什么从 A 切到 B，要说得清楚。
2. 为什么这帧允许取消，下一帧不允许，要说得清楚。
3. 为什么底盘保留、上半身切换、Additive 继续叠加，要说得清楚。

一旦过渡逻辑只能靠当前播放的那一个动画状态来反推，系统就很难做大。

## 3. 为什么单层状态机做不到这件事

单层状态机的问题，不是简单或者老，而是表达维度不够。

如果一个角色任意时刻只有一个主状态，那么它隐含了三个危险前提：

1. 当前行为只有一条主线。
2. 当前动画只有一个主要来源。
3. 状态切换就等于动画切换。

这在简单项目里可以成立，但在高规格 ARPG 里会立即遇到问题。

### 3.1 运动与动作天然不是一条线

“角色当前在跑” 和 “角色当前在挥刀” 不是同一维度的信息。

前者回答的是：

1. 当前底盘姿态是什么。
2. 是否接地。
3. 是否还能转向。
4. 是否还能持续移动。

后者回答的是：

1. 当前在执行什么动作。
2. 动作处于起手、执行还是收招。
3. 是否可取消。
4. 是否允许派生下一段动作。

如果把这两类问题塞进同一个状态名里，状态数量会指数级膨胀。

### 3.2 单状态无法稳定支撑分层动画

当你想表达“跑动中上半身攻击”时，单状态机通常只能走两条路：

1. 新建一个 `RunAttack` 状态。
2. 让攻击状态完全覆盖跑动状态。

第一条路会导致状态爆炸。

第二条路会导致底盘信息丢失。

这就是为什么真正的分层动画，几乎总是对应多条状态线，而不是一个万能状态枚举。

### 3.3 过渡规则会越来越脏

单状态模型一旦做复杂，最后都会出现下面这种问题：

1. 某些状态为了兼容移动，不得不写例外。
2. 某些状态为了兼容受击，不得不写例外。
3. 某些状态为了兼容闪避和落地，又得继续写例外。

最后你看到的不是状态机，而是一个“状态 if else 集合体”。

## 4. 顶级 ARPG 动画框架应该怎么设计

如果目标是高规格 ARPG，比较稳妥的方向不是先定义一堆类，而是先建立下面这套结构观。

### 4.1 先分成三层问题

无论最终类怎么命名，底层都应该至少分清三类问题：

1. 规则层：当前允许发生什么。
2. 运动层：当前这一帧怎么移动、怎么转向。
3. 表现层：当前各动画层播什么、怎么切、怎么叠。

高规格动作系统的关键不是把三者完全隔离，而是让它们之间的依赖方向稳定。

正确的关系应该是：

1. 规则层决定资格与所有权。
2. 运动层执行位移与转向。
3. 表现层消费状态结果，组织动画播放。

而不是让动画播放器反过来承担规则判断。

### 4.2 至少两条正交状态线

如果当前阶段主要解决动画播放与切换，那么最少也要引入两条正交状态线：

1. Locomotion 状态线。
2. Action 状态线。

这是最小可行骨架，不是最终上限。

#### 4.2.1 Locomotion 状态线

负责底盘行为。

它主要表达：

1. Idle
2. Walk
3. Run
4. Sprint
5. Jump
6. Falling
7. Land

这条线的价值不在“播这些动画”，而在于它稳定表达了底盘事实：

1. 当前是否接地。
2. 当前是否允许普通移动。
3. 当前是否允许转向。
4. 当前底盘动画应该由哪类 BlendTree 或动作集驱动。

#### 4.2.2 Action 状态线

负责高优先级动作行为。

它主要表达：

1. None
2. Skill
3. Dodge
4. HitReact
5. Knockdown
6. SpecialAction

这条线的价值不在“动作名字”，而在于它稳定表达了动作事实：

1. 当前动作的阶段。
2. 当前动作的取消规则。
3. 当前动作是否接管移动。
4. 当前动作是否接管转向。
5. 当前动作应该写入哪个动画槽位。

### 4.3 由状态线驱动动画槽位，而不是由单状态直接播动画

真正高级的做法，不是“一个状态直接 Play 一个 Clip”，而是：

1. 各状态线先产出自己的表现请求。
2. 表现层再把请求路由到不同槽位。
3. 每个槽位独立处理切换、混合、保持、抢占和恢复。

最少应该预留这些槽位：

1. Locomotion 槽
2. Action 槽
3. Additive 槽
4. 可选 UpperBody 槽

这样才能表达：

1. 底盘继续跑，动作槽切攻击。
2. 动作槽继续播，Additive 槽叠加轻受击。
3. 上半身独立执行某个动作，而底盘不丢。

### 4.4 动画切换要以“请求模型”组织，而不是裸播 Clip

当前阶段如果只关心动画播放与切换，最重要的一点是不要再让业务层直接控制底层播放对象。

应该改成：

1. 状态层只发“动画请求”。
2. 请求里说明目标槽位、动画资产、过渡参数、是否可抢占、是否保持时间同步。
3. 动画控制器统一消费这些请求。

否则后面一旦加上分层、Mask、Additive、RootMotion 策略，所有调用点都要重写。

### 4.5 切换规则必须先于播放接口设计

很多项目会先做 `Play`、`CrossFade`、`Stop`，最后再补规则。

这个顺序通常会出事。

更合理的是先定义：

1. 谁可以抢占谁。
2. 谁结束后恢复谁。
3. 谁只是叠加，谁是真覆盖。
4. 什么情况下保留当前槽位时间，什么情况下强制重播。

然后再决定底层动画控制器暴露哪些播放接口。

### 4.6 RootMotion 必须是策略，不是动画顺带产物

虽然当前阶段主要解决播放与切换，但如果目标真的是高规格 ARPG，就必须提前留出 RootMotion 的归属位。

正确思路不是“某个动画带 RootMotion，所以角色就跟着走”，而是：

1. 当前动作是否拥有位移权。
2. 当前动作是否拥有转向权。
3. RootMotion 的平移和旋转是否分别启用。
4. 是全量接管，还是只取部分轴向。

否则后面动画切得再漂亮，手感也会被位移控制打烂。

## 5. 为什么当前阶段就要引入分层状态机

当前阶段虽然只想先解决动画播放和切换，但这恰恰是最适合引入分层状态机的时候。

原因很简单：

1. 如果先按单状态机继续堆动画播放接口，后面分层时一定要推倒重来。
2. 如果现在先把状态表达拆开，哪怕一开始只接两个槽位，后面也能自然扩展。
3. 动画播放器要想做对，必须先知道它要服务的是“几条状态线”，而不是“几个状态名”。

也就是说，分层状态机不是后续高级功能，而是动画系统从“单轨脚本播放器”升级成“可扩展 3C 表现层”的前置条件。

---

## 6. 当前阶段的最小落地目标

这阶段不要贪大，不直接追求完整终局，而是先把最关键的骨架立住。

当前阶段的最小目标应该是：

1. 运行时支持至少两条状态线：Locomotion 和 Action。
2. 动画系统支持至少两个主要槽位：Locomotion 和 Action。
3. 状态层输出动画请求，而不是直接操作底层 AnimancerState。
4. Action 槽能够覆盖或挂起底盘动画，但不会销毁 Locomotion 的状态事实。
5. 动作结束后能够稳定恢复到底盘状态，而不是重新猜当前应该播什么。

如果这五件事做稳了，后续再加：

1. UpperBody
2. Additive
3. HitReact 叠层
4. RootMotion 轴向策略
5. 动作取消和派生规则

都会顺很多。

---

## 7. 当前结论

如果目标是顶级 ARPG 的 3C 动画框架，那么设计方向不应该是：

1. 继续强化单层唯一状态机。
2. 继续围绕单一动画播放状态扩展接口。
3. 继续让技能运行时直接控制动画实现细节。

而应该是：

1. 用至少两条正交状态线表达角色行为。
2. 用动画槽位而不是单轨播放表达角色表现。
3. 用统一动画请求模型驱动播放和切换。
4. 让动画系统只负责表现，不再承担规则层职责。

当前阶段的核心结论只有一句话：

要想把动画播放和切换做对，就必须先把角色行为从“单状态”升级成“分层状态”。

下一步再继续讨论时，重点就不该是“要不要分层”，而是：

1. 这两条状态线各自的最小数据结构是什么。
2. 动画请求模型最少需要哪些字段。
3. Locomotion 槽和 Action 槽的覆盖与恢复规则怎么定义。
