# 分层状态机设计 v2

## 1. 这份文档要解决什么

本文档用于替换当前项目里“Locomotion/Action 半特化分层状态机”的旧方案，明确后续第一版实现应该遵守的最小设计。

这次调整后的目标非常明确：

1. 状态机支持多层，但层与层之间的状态推进互不直接影响。
2. 任意一层切换状态，不会冻结其他层，不会强制把其他层切回默认态。
3. 状态层仍然使用固定枚举，第一版只定义 Locomotion 和 Action 两层。
4. 层有固定优先级，优先级高的层可以覆盖低优先级层的表现输出。
5. 动画层和状态层分开建模。
6. 第一版动画只支持 Locomotion 和 Action 两个动画层。
7. 第一版先不引入 ability 概念，也不引入基于 tag 的能力系统。

本文档只描述新的设计，不描述兼容旧实现的过渡细节。

---

## 2. 对当前设计的结论

当前工程中的实现有三个核心问题：

1. 状态层被特殊化了。
2. 层间影响通过 SharedControlContext 这种中间汇总结构表达。
3. 动画播放仍然倾向于“选一个主状态负责表现”。

这会带来几个结构性后果：

1. 控制器天然知道 Locomotion 和 Action 的特殊规则，难以扩展更多层。
2. 某一层的状态切换，容易演变成对另一层的直接干预。
3. 表现层不是在做动画融合，而是在做“主状态替换”。

这与新的设计目标不一致。

新的方向应该是：

1. 状态机只负责维护“每一层当前是什么状态、如何独立推进、如何独立切换”。
2. 层之间不直接修改彼此状态。
3. 层的优先级只影响表现仲裁，不影响其他层是否继续推进。
4. 动画层负责表现覆盖与融合，不负责改变其他状态层的运行时。

---

## 3. 新方案的核心原则

## 3.1 状态层独立推进

任意状态层都必须满足以下规则：

1. 拥有自己的当前状态。
2. 拥有自己的时间推进。
3. 拥有自己的中断评估。
4. 拥有自己的自然结束处理。

某一层进入新状态时：

1. 不冻结其他层的时间推进。
2. 不要求其他层立即切换默认态。
3. 不直接重置其他层的动画时间。

这意味着：

1. `Action` 层进入技能状态时，`Locomotion` 层继续正常推进。
2. `Locomotion` 层进入跑步、停下、转身，不直接改变 `Action` 层的状态。

---

## 3.2 层与层之间只通过优先级影响表现输出

层与层之间可以发生影响，但这种影响不是“直接改对方状态”，而是“更高优先级层覆盖更低优先级层的输出结果”。

第一版当前只讨论表现输出，不讨论 ability 或控制输出。

表现输出例如：

1. 当前应该播放哪个动画层。
2. 当前脚步表现是否仍然可见。
3. 当前移动特效是否仍然可见。

第一版先采用最简单的优先级仲裁规则：

1. 层按优先级从高到低排序。
2. 表现求值时，优先读取最高优先级活动层的定义。
3. 低优先级层继续运行，但其表现可能被高优先级层覆盖。

---

## 3.3 状态层固定枚举，但运行时不能写死分支逻辑

第一版不做动态添加层级。

状态层使用固定枚举：

1. `Locomotion`
2. `Action`

并固定优先级：

1. `Locomotion = 0`
2. `Action = 1`

但这不代表运行时可以写成大量特判分支。

需要避免的写法是：

1. `TickLayer(StateLayerType.Locomotion)`
2. `TickLayer(StateLayerType.Action)`

第一版正确方向是：

1. 控制器内部维护一个层集合。
2. 层集合按优先级排序。
3. `Tick`、中断评估、自然结束都用统一循环遍历层集合。

也就是说，层级是固定枚举，运行逻辑仍然要普适。

---

## 3.4 UnitConfig 需要按层定义默认状态

旧的 `UnitConfig.DefaultStateId` 只适合单层状态机。

新的第一版里，`UnitConfig` 必须按层定义默认状态。

也就是要能明确回答：

1. `Locomotion` 层默认状态是什么。
2. `Action` 层默认状态是什么。

推荐规则：

1. `Locomotion` 层必须有默认状态。
2. `Action` 层可以为空，表示默认没有活动状态。

---

## 3.5 动画层和状态层分开建模

这次设计里，“状态层”和“动画层”必须明确拆开。

状态层解决的是：

1. 当前层在哪个状态。
2. 当前层怎么推进。
3. 当前层何时切换。

动画层解决的是：

1. 当前状态输出到哪个动画混合槽。
2. 这个槽如何与其他槽融合。
3. 哪个槽覆盖哪个槽。

第一版状态层虽然只有固定两层，但动画层仍应与状态层分开。
第一版动画层先只支持两个固定槽：

1. Locomotion
2. Action

未来可扩展：

1. UpperBody
2. Additive

但第一版先不做这两个。

---

## 4. 第一版范围

## 4.1 第一版状态机必须完成的内容

1. 支持角色同时拥有 `Locomotion` 与 `Action` 两个状态层。
2. 支持每个状态定义自己的所属层。
3. 支持固定优先级定义。
4. 支持每层独立推进与独立切换。
5. 支持按优先级仲裁当前角色的动画表现输出。

## 4.2 第一版动画必须完成的内容

1. 动画配置支持声明动画输出层。
2. 支持 Locomotion 动画层持续播放。
3. 支持 Action 动画层覆盖 Locomotion 的表现。
4. Action 覆盖只影响表现，不影响 Locomotion 状态继续推进。

## 4.3 第一版明确暂不解决的内容

1. Ability 系统。
2. UpperBody 动画层。
3. Additive 动画层。
4. 基于 tag 的状态能力系统。
5. 跨层控制门禁求解。

第一版先立住骨架，而不是一次性解决所有控制语义。

---

## 5. 第一版状态层模型

## 5.1 状态层用固定枚举定义

第一版状态层明确使用固定枚举：

```csharp
public enum StateLayerType
{
	None = 0,
	Locomotion = 1,
	Action = 2,
}
```

并固定优先级：

1. `Locomotion = 0`
2. `Action = 1`

这里的重点不是动态扩展，而是先把运行时逻辑写成“遍历层集合”的统一形式。

## 5.2 状态归属层

每个 State 必须声明自己的 `StateLayerType Layer`。

例如：

1. `idle` 属于 `Locomotion`
2. `run` 属于 `Locomotion`
3. `skill_1_cast` 属于 `Action`
4. `dodge` 属于 `Action`

## 5.3 状态层独立运行的后果

当 `action` 层切到 `skill_1_cast` 时：

1. `locomotion` 层当前状态继续存在。
2. `locomotion` 层时间线继续推进。
3. `locomotion` 层自然结束逻辑继续生效。
4. `locomotion` 层中断逻辑继续生效。

但它的表现可能被 `action` 层覆盖。

---

## 6. 第一版先不定义 Ability / 控制语义

第一版设计里，不把 `SharedControlContext` 继续发展成正式模型，也不在这一轮引入 `StateControlProfile` 或 ability。

这一版只解决两件事：

1. 状态层如何分层推进。
2. 动画表现如何按层覆盖。

移动、旋转、输入锁、tag 求解，这一版全部延后。

这是“高层覆盖输出，不修改低层状态”的典型例子。

---

## 7. 第一版动画分层

## 7.1 只做两个动画层

第一版动画混合层只做：

1. Locomotion
2. Action

它们的规则如下：

1. Locomotion 负责底盘动画基础表现。
2. Action 权重为 1，直接覆盖 Locomotion 的表现输出。
3. 覆盖只发生在表现层，不影响 Locomotion 的状态推进。

## 7.2 第一版典型场景

角色处于：

1. `locomotion/run`
2. `action/skill_1_cast`

此时系统行为应该是：

1. `run` 状态仍在推进。
2. `skill_1_cast` 状态也在推进。
3. 画面表现以 Action 动画为主。
4. 脚步表现、移动特效可以被 Action 覆盖掉。
5. 技能结束后，Action 动画退出，Locomotion 表现自然恢复。

这里没有“把 locomotion 切回 idle”的额外步骤。

---

## 8. 与旧方案最关键的差异

新的设计与旧方案相比，有四个本质差异：

1. 旧方案把状态层和特定业务规则绑死，新方案把状态层变成可扩展配置。
2. 旧方案允许某层通过共享控制或显式逻辑直接影响另一层状态，新方案只允许通过优先级影响输出。
3. 旧方案把 SharedControlContext 当成正式语义承载，新方案把它降级为过渡实现细节，正式语义转为“层优先级 + 层输出定义”。
4. 旧方案动画仍偏向主状态驱动，新方案明确是 Locomotion 与 Action 的表现覆盖关系。

---

## 9. 第一版落地顺序建议

如果后续进入实现，建议严格按下面顺序推进：

1. 先重定义状态层与动画层的数据结构。
2. 再去掉 StateController 里对 Locomotion / Action 的硬编码特判。
3. 再让状态切换与 Tick 真正按“多层独立推进”运行。
4. 最后才改动画桥，让 Locomotion 与 Action 两个动画层按覆盖关系工作。

不要倒过来先补表现层临时逻辑，否则会继续把旧设计拖长。

---

## 10. 当前设计结论

第一版最重要的不是把所有能力系统一次做完，而是把下面这三件事做对：

1. 状态机层可扩展。
2. 各层独立推进、互不直接改状态。
3. 动画先做 Locomotion 与 Action 两层覆盖关系。

只要这三件事做对，后续再把 ability、tag、upperbody、additive 一点点加上去，结构仍然是稳的。
