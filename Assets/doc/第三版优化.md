# 第三版优化

## 1. 结论

第三版后续优化的核心结论只有一条：

`State` 必须回到 `StateController` 统一管理。

`Skill` 不是 `State` 的管理者，`Skill` 只是：

1. 一个决定“是否可以请求进入某个技能 State”的外部系统。
2. 一个在状态变化后调整自身技能流转的外部系统。
3. 一个承载技能资源、CD、连段、元技能图流转的业务系统。

因此：

1. 技能系统可以决定是否发起“进入技能状态”的请求。
2. 技能系统可以监听状态变化，从而推进自己的技能链逻辑。
3. 一旦某个技能 State 已经进入，后续的 interrupt、default next、自然结束、动画推进、状态退出清理，都必须走 `StateController` 的统一管线。

这条原则必须压过一切临时修补。

---

## 2. 本次需要否定的做法

本次已经验证出一个不应继续扩展的方向：

在 `MetaSkillRuntime` 中复制一份类似 `StateController` 的状态运行逻辑。

该做法的问题不是“短期能不能跑”，而是结构上错误：

1. `State` 的生命周期被拆成两套执行中心。
2. `InterruptTracks`、`DefaultNextStateId`、自然结束、loop 窗口、预输入缓存等逻辑会出现双份实现。
3. 后期任何状态规则新增或修正，都需要同时修改 `StateController` 和 `MetaSkillRuntime`。
4. 技能相关问题和状态相关问题会互相污染，排查边界越来越不清晰。
5. 最终会形成“表面上是 State，实际上只有普通 State 和技能内嵌 State 两套语义”的维护灾难。

因此第三版优化明确规定：

1. `MetaSkillRuntime` 不再承担内嵌 State 的 interrupt/default-next 语义。
2. `MetaSkillRuntime` 不再维护缩小版的状态切换器。
3. 所有 State 切换都必须通过 `StateController.CommitTransition(...)` 归一。

---

## 3. 问题重新定义

当前结构里真正的问题不是“打断轨为什么没触发”。

真正的问题是：

`MetaSkill` 目前把 `skillState/recoveryState` 当成了技能自己的内部播放片段，而不是单位状态机中的正式状态。

这导致它在运行时上有三个错位：

1. `MetaSkillRuntime` 控制了 `State` 的推进。
2. `StateController` 看不到这两个内嵌 `State` 的激活与退出。
3. 技能系统和状态系统的职责边界被打穿。

而用户期望的正确模型其实非常清楚：

1. 玩家按下 Q。
2. 输入系统或技能系统判断：当前是否允许请求进入某个技能 State。
3. 若允许，则向 `StateController` 发起一次切换请求。
4. 进入该技能 State 后，这个 State 和普通跑步、受击、待机 State 没有本质区别。
5. 它后续怎么被打断、什么时候结束、结束后去哪，都是 `StateController` 的职责。
6. 技能系统只根据状态变化结果，推进技能链或终止技能链。

---

## 4. 第三版优化后的职责划分

## 4.1 Skill 系统职责

`SkillRuntime` / `MetaSkillRuntime` 保留以下职责：

1. 技能资源检查。
2. CD 检查。
3. 技能槽位与输入事件匹配。
4. 技能图节点流转。
5. 选择“下一段技能应请求进入哪个 State”。
6. 根据状态结果决定技能链继续、等待 continuation、或终止。
7. 处理技能专属效果树、调试快照、技能级 trace。

`Skill` 不再负责：

1. 技能 State 的 interrupt 判定。
2. 技能 State 的 default next 处理。
3. 技能 State 的自然结束判断。
4. 技能 State 的退出清理。
5. 技能 State 的动画生命周期裁决。

## 4.2 State 系统职责

`StateController` 统一负责：

1. 当前激活 State 是谁。
2. State 的时间推进。
3. StateTimeline 的推进。
4. InterruptTracks 与 Interrupts 的扫描。
5. 输入/命中/被击/BreakValue 的条件判定。
6. 自然结束与 `DefaultNextStateId`。
7. 状态进入、退出、动画切换、标签清理。
8. 所有内部打断与外部请求的统一提交。

## 4.3 Skill 与 State 的交界面

第三版优化后，Skill 和 State 之间的关系应当降维成“请求”和“通知”。

Skill -> State：

1. 请求进入某个技能 State。
2. 请求是否允许从当前状态切到某个技能 State。
3. 必要时请求强制进入某状态。
4. 在 useMetaSkill 成功启动时，先执行 OnAddEffect，再发起技能 State 切换请求。

State -> Skill：

1. 通知当前进入了哪个状态。
2. 通知某个技能 State 已正常结束。
3. 通知某个技能 State 已被打断。
4. 通知当前状态是否仍属于某个技能链上下文。
5. 通知里必须带上 SkillId、MetaSkillId、阶段角色和结束原因。

Skill 不直接操纵 State 内部运行细节。

---

## 5. 目标架构

## 5.1 核心思路

把 `MetaSkill` 的 `skillState/recoveryState` 从“内嵌状态片段”改回“正式 State 引用或正式 State 身份”。

第三版推荐理解方式：

1. 一个 `MetaSkill` 对应一段技能业务语义。
2. 这段业务语义会关联一个或多个正式 `State`。
3. `StateController` 负责让这些 `State` 真正运行。
4. `MetaSkillRuntime` 只负责跟踪“当前技能链期待中的 State 阶段”是否已经进入、完成、被打断。

## 5.2 推荐结构

建议将 `MetaSkill` 的 execute/recovery 理解成两个正式的状态目标：

1. `ExecuteStateId`
2. `RecoveryStateId`

如需继续保留编辑器内嵌配置体验，也只能是编辑器层面的资源组织方式，不能是 runtime 的双轨执行中心。

也就是说：

1. 编辑器可以允许在 `MetaSkill` 界面里编辑 `skillState/recoveryState`。
2. 但保存后，runtime 必须把它们视为正式 State 数据。
3. 正式运行时，必须由 `StateController` 激活这些 State。

---

## 6. 运行时主流程

## 6.1 技能起手

技能起手流程应当改为：

1. 输入系统产生 Q/短按/长按等输入事件。
2. `SkillRuntime` 根据技能槽位、CD、资源、技能图规则判定，是否允许起手。
3. 若允许，`SkillRuntime` 不直接创建并运行一个内部 execute state runtime。
4. `SkillRuntime` 向 `StateController` 提交一次外部状态切换请求，目标是当前技能节点的 `ExecuteStateId`。
5. 若 `StateController` 接受该请求，则技能链正式进入 casting 状态。
6. 若 `StateController` 拒绝该请求，则本次技能起手失败。

本质上，这一步和“输入系统请求切到跑步 State”没有原则区别，只是 Skill 系统多做了资源/CD/技能图判定。

补充约束：

1. 如果 useMetaSkill 已经成功启动，则 OnAddEffect 应在请求状态切换前执行。
2. 技能 State 是否被接受进入，由 StateController 统一裁决。
3. 技能系统不能在内部私自推进 execute/recovery 的状态时间，而是等待 StateController 的状态结果通知。

## 6.2 技能状态运行

一旦进入技能 Execute State，后续流程全部归 `StateController`：

1. 推进时间轴。
2. 播放动画。
3. 检查 interrupt。
4. 处理 default next。
5. 决定是否切到 Recovery State 或别的普通 State。

此时 `SkillRuntime` 不再自己维护 execute/recovery 的状态时间。

## 6.3 技能状态结束

当技能 State 结束时，可能出现三种情况：

1. `DefaultNextStateId` 指向同一技能链的 Recovery State。
2. `DefaultNextStateId` 指向外部普通 State。
3. 被 interrupt 切到了别的 State。

这三种情况的共同点是：

都由 `StateController` 先落地状态切换，再由 Skill 系统观察结果并决定自己的后续行为。

正确顺序必须是：

1. `StateController` 完成状态切换。
2. Skill 系统收到状态变化结果。
3. Skill 系统更新当前 MetaSkill/Node/Continuation 状态。

如果是被打断路径，则还必须补上：

1. StateController 明确通知“当前技能 State 被中断”。
2. Skill 系统将当前 MetaSkill 标记为 interrupted end。
3. 当前 MetaSkill 的 OnEndEffect 被跳过。
4. Skill 系统根据 continuation 规则决定是否开放下一段技能输入。

而不是反过来先由 SkillRuntime 决定“我进入 recovery 了”，再去驱动状态系统配合它。

---

## 7. StateController 需要新增的能力

第三版优化不是让 `MetaSkillRuntime` 更复杂，而是让 `StateController` 补齐对技能请求的正式支持。

## 7.1 外部请求需要带来源语义

现有 `TryChangeState/ForceChangeState` 可以继续保留，但建议补充来源语义，例如：

1. `InputDriven`
2. `SkillDriven`
3. `BuffDriven`
4. `ScriptDriven`

目的不是分叉提交逻辑，而是：

1. 便于调试 trace。
2. 便于后续做状态切换统计。
3. 在不破坏统一 `CommitTransition(...)` 的前提下保留请求来源信息。

## 7.2 技能请求上下文

建议增加技能请求上下文，例如：

1. SkillId
2. MetaSkillId
3. SkillNodeId
4. RequestedStateId
5. 是否为 continuation
6. 对应输入事件

这部分数据不应改变 State 切换语义，只用于：

1. 让 Skill 系统在状态回调时知道“这是哪次技能请求”。
2. 让调试系统能看到“哪个技能请求切进了哪个状态”。

## 7.2.1 技能流上下文不能因状态切换而丢失

这是第三版优化里的硬约束。

把技能 State 交回 `StateController` 管理，只意味着：

1. State 的进入、退出、打断、default-next 归 `StateController`。
2. 不再由 `MetaSkillRuntime` 私自维护一套 State 生命周期。

这不意味着技能流上下文可以跟着丢失。

必须明确区分两种东西：

1. `State` 生命周期。
2. 技能流上下文生命周期。

二者不是同一个东西。

正确模型应是：

1. 一次技能起手成功后，创建一份“本次技能流上下文”。
2. 这份上下文独立于当前激活的具体 State 存活。
3. execute state、recovery state、continuation state 都只是这份技能流上下文在不同阶段挂接到的正式 State。
4. 只要这次技能链还没有被判定结束，这份上下文就必须继续存在。
5. 状态切换到同一技能链内的下一个 State 时，上下文不重建、不清空、不丢失。
6. 只有当整条技能链终止、取消、超时、或被判定彻底退出技能系统时，这份上下文才允许销毁。

因此，像下面这种需求必须天然成立：

1. 第二段技能 State 可以拿到它所属的 Skill。
2. 第二段技能 State 可以拿到本次技能流第一段造成的伤害结果。
3. 当前攻击盒命中后，可以基于前段伤害、命中目标、累计层数、前段事件结果等上下文决定本段额外效果。

也就是说：

State 是正式 State，
但它仍然必须能访问“我属于哪次技能流”。

## 7.2.2 建议新增 SkillFlowContext

为避免把这类数据继续散落在 `MetaSkillRuntime` 的私有字段或临时黑板里，建议显式抽出：

`SkillFlowContext`

建议至少包含：

1. `SkillId`
2. `MetaSkillId`
3. `SkillNodeId`
4. `FlowRuntimeId`
5. `StartedAtTime`
6. `CurrentStageStateId`
7. `EntryInputEvent`
8. `PreviousMetaSkillResults`
9. `AccumulatedEffectResults`
10. `FlowBlackboard`

其中：

1. `PreviousMetaSkillResults` 用于记录上一段或前几段元技能的关键结算结果。
2. `AccumulatedEffectResults` 用于记录本次技能流全过程的命中/伤害/附加效果摘要。
3. `FlowBlackboard` 用于承载需要跨 State 延续的技能链局部变量。

这份 `SkillFlowContext` 应由 Skill 系统创建和销毁。

但它不负责 State 切换。

## 7.2.3 State 如何访问 SkillFlowContext

建议运行时关系是：

1. `SkillRuntime` 在技能起手成功后创建 `SkillFlowContext`。
2. `SkillRuntime` 在向 `StateController` 发起技能 State 请求时，把 `SkillFlowContext` 作为请求上下文的一部分带过去。
3. `StateController` 提交切换后，将该上下文挂到当前激活 State 对应的运行时上下文上。
4. StateTimeline、攻击盒、事件节点、效果树执行时，都通过当前 `SkillContext` 或当前 `StateRuntimeContext` 读取这份 `SkillFlowContext`。
5. 当状态切到同一技能链的下一段 State 时，沿用同一份 `SkillFlowContext`。
6. 当状态切到与当前技能链无关的外部普通 State，且 Skill 系统判定技能链终止时，再释放这份上下文。

这里的关键点是：

不是 State 自己保存技能流，
而是 State 拿到一份对当前技能流上下文的引用。

这样才能保证：

1. State 仍由 `StateController` 管理。
2. Skill 流上下文仍由 Skill 系统持有。
3. 二者通过稳定引用关联，而不是互相越权接管生命周期。

## 7.3 状态变化通知

`StateController` 需要向 Skill 系统暴露可订阅的状态变化通知，至少包括：

1. `OnStateEntered`
2. `OnStateExited`
3. `OnStateTransitionCommitted`

Skill 系统后续根据这些通知做技能链流转，而不是自己在 `MetaSkillRuntime.Tick()` 中推断状态是否已经结束。

---

## 8. MetaSkillRuntime 的收缩方向

第三版优化后，`MetaSkillRuntime` 应明显收缩，而不是继续膨胀。

## 8.1 保留的职责

`MetaSkillRuntime` 保留：

1. 技能级效果树触发，例如 OnAdd / OnEnd。
2. 与当前技能图节点相关的调试信息。
3. 与技能上下文相关的状态监听桥接。
4. 恢复 carryover 这类纯技能特有的运行时残留处理。

## 8.2 移除的职责

`MetaSkillRuntime` 必须移除：

1. execute/recovery 两段内部 `ActiveStateRuntime`。
2. interrupt 扫描逻辑。
3. default-next 裁决逻辑。
4. 自然结束判断逻辑。
5. “是否跳到 recovery 或外部 state”的决定权。

这些都应回收给 `StateController`。

## 8.3 MetaSkillRuntime 的新定位

`MetaSkillRuntime` 在第三版优化后应是：

“技能链上下文观察器 + 技能级副作用执行器”，而不是“内嵌 State 调度器”。

---

## 9. SkillRuntime 的改造方向

## 9.1 从主动驱动状态变成响应状态

当前 `SkillRuntime` 更像“主动推动 MetaSkill 每段执行完成”。

优化后应改为：

1. 技能起手时，请求 `StateController` 进入 Execute State。
2. 进入成功后，把当前技能链标记为激活。
3. 监听状态进入/退出/切换结果。
4. 若当前技能链对应的 Execute State 切到 Recovery State，则认为技能进入恢复段。
5. 若切到外部普通 State，则认为本段技能已被中断或正常结束。
6. continuation 是否开放，也由“状态机是否走到对应窗口/对应状态”决定，而不是由内部 MetaSkill timer 再算一份。

## 9.2 技能门禁与状态门禁分离

必须严格区分两类问题：

1. 技能系统门禁：我现在能不能请求进入这个技能 State。
2. 状态系统门禁：当前 State 是否允许切到目标 State。

第一类由 Skill 系统负责，例如：

1. CD 是否结束。
2. 资源是否足够。
3. 技能图当前节点是否允许起手。
4. 是否命中某个 continuation 规则。

第二类由 State 系统负责，例如：

1. 当前状态 interrupt 窗口是否允许切到该技能 State。
2. 当前状态条件是否满足。
3. 是否存在强制打断。

这两类不能混在一个 runtime 里重复判断。

---

## 10. 数据模型调整建议

## 10.1 MetaSkill 数据

建议 `MetaSkillConfig` 在 runtime 语义上弱化“内嵌 State 数据载体”的身份，强化“状态引用关系”的身份。

推荐至少显式具备：

1. `ExecuteStateId`
2. `RecoveryStateId`
3. `StatesOfCanInterrupt` 或更名为技能起手允许状态列表
4. 技能级效果树配置
5. 技能链元信息

如果编辑器仍然保留内嵌 `StateConfig`，则必须明确：

1. 这是编辑期资源组织形式。
2. Runtime 最终仍以 StateController 注册的正式 State 为准。

## 10.2 SkillContext 数据

`SkillContext` 不应继续承载一套“供 MetaSkillRuntime 自己实现 State 语义”的 provider 集合。

优化后：

1. `SkillContext` 可以继续持有 `StateController` 引用。
2. `SkillContext` 必须可以持有当前 `SkillFlowContext` 引用。
3. `SkillContext` 可以持有当前技能链上下文的运行时快照与黑板。
4. 但输入/命中/被击/BreakValue 的运行时采样，应以 `StateController` 为主消费方。

Skill 系统若需要读取状态快照，应通过状态系统公开的数据结果读取，而不是自己重新跑一份状态判定。

需要特别强调：

1. `SkillContext` 保留，不因为 State 回归 `StateController` 而消失。
2. 当前激活的技能 State 在执行攻击盒、事件、效果树时，必须能通过 `SkillContext` 拿到所属 Skill 和所属 `SkillFlowContext`。
3. 因此前段元技能伤害、前段命中结果、累计层数、前段效果回执等跨段信息，必须能被后续技能 State 正常读取。
4. 这属于技能流上下文传递问题，不属于 State 生命周期管理问题。

---

## 11. 推荐事件流

推荐把第三版的核心运行流收敛成下面的事件关系：

1. 输入系统发出输入事件。
2. Skill 系统匹配技能槽位并做技能门禁校验。
3. Skill 系统向 `StateController` 请求切到 Execute State。
4. `StateController` 统一检查当前状态是否允许切换，并提交 transition。
5. `StateController` 驱动 Execute State 正式运行。
6. 运行中若命中 interrupt/default-next，仍由 `StateController` 统一切换。
7. 状态切换结果通过事件通知给 Skill 系统。
8. Skill 系统据此更新当前技能节点、recovery 阶段、continuation 可用性和技能结束状态。

这个事件流中，状态系统是状态真相来源，技能系统不是。

## 12. 具体实施方案

## Phase 1：职责回正

目标：先把设计边界重新站稳。

动作：

1. 冻结并否定 `MetaSkillRuntime` 中新增的缩小版 state 切换逻辑。
2. 明确 `StateController` 是唯一状态执行中心。
3. 把第三版文档中的相关表述统一成“Skill 请求状态，StateController 管状态”。

出口条件：

1. 文档层不再存在“MetaSkillRuntime 驱动内嵌 State 语义”的描述。

## Phase 2：StateController 接技能请求

目标：让技能系统能正式向状态系统发请求。

动作：

1. 为 `StateController` 增加带来源语义的状态切换请求接口。
2. 加入技能请求上下文。
3. 打通状态切换 trace 与调试快照。

出口条件：

1. 技能起手能通过 `StateController` 正式进入技能 Execute State。

## Phase 3：SkillRuntime 改为状态驱动

目标：让技能链流转依赖状态结果，而不是技能内部私有 timer。

动作：

1. `SkillRuntime` 请求切状态而不是直接内部运行 execute/recovery。
2. `SkillRuntime` 监听状态进入/退出/切换。
3. continuation 逻辑改为由状态变化结果驱动。

出口条件：

1. Execute/Recovery 的进入与退出不再由 `MetaSkillRuntime` 自己裁决。

## Phase 4：收缩 MetaSkillRuntime

目标：把状态语义全部剥离出去。

动作：

1. 移除 `MetaSkillRuntime` 内部 state runtime。
2. 移除 interrupt/default-next/natural-end 复制逻辑。
3. 保留技能级效果和观察职责。

出口条件：

1. `MetaSkillRuntime` 只剩技能级逻辑，不再重复 `StateController`。

## Phase 5：编辑器与数据收口

目标：让编辑体验仍然方便，但 runtime 结构单一。

动作：

1. 明确编辑器内嵌 State 与正式 State 资源的映射策略。
2. 明确保存、迁移、引用关系。
3. 清理旧的 timeline-only 运行时残留语义。

出口条件：

1. 编辑期可内嵌编辑，运行期只认正式状态机语义。

---

## 13. 禁止事项

第三版优化后，以下做法一律视为错误方向：

1. 在 `SkillRuntime` 或 `MetaSkillRuntime` 再复制一份状态切换规则。
2. 让技能系统直接裁决某个 State 的 interrupt 是否命中。
3. 让技能系统单独维护 execute/recovery 的状态 elapsed time，并拿它和 `StateController` 并行运行。
4. 用“技能结束时强制切 idle”之类的补丁替代正式状态流转。
5. 把 continuation 逻辑写成绕过状态系统的直接跳段逻辑。

---

## 14. 最终原则

第三版优化必须收束到一句最朴素的话：

状态由状态系统管理，技能由技能系统管理。

技能系统可以影响状态切换。
状态系统也可以反过来影响技能流转。

但二者都不能越权替代对方。

对第三版来说，这不是风格偏好，而是后续还能不能维护的基础前提。
