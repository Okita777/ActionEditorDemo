# 散爆 Unity 战斗/3C 开发岗位面试锦囊

## 1. 岗位画像

### 1.1 岗位本质

这不是普通 Unity 功能开发岗，而是偏中高级的：

> Unity 战斗 Gameplay / 3C 客户端开发工程师

核心职责围绕联网射击或动作项目展开：

- 战斗系统；
- 技能、枪械与弹道；
- Character、Camera、Control；
- 动画与操作手感；
- Dedicated Server 同步；
- 弱网与断线问题；
- 性能分析和优化；
- 战斗模块长期迭代与缺陷治理。

岗位要求“独立完成相关模块开发兼性能调优”，意味着候选人需要具备完整模块 Owner 能力：

1. 理解并拆解需求；
2. 设计模块边界和数据结构；
3. 完成运行时实现；
4. 与策划、美术、动画和服务端联调；
5. 使用数据定位性能问题；
6. 处理测试和线上阶段的复杂缺陷；
7. 对模块长期维护负责。

### 1.2 招聘信息里的强信号

| 招聘表述 | 隐含需求 |
|---|---|
| 战斗系统模块开发 | 需要完整 Gameplay 架构能力，不只是写零散功能 |
| 技能/枪械/手感/弹道/3C | 岗位核心是战斗体验和角色控制 |
| 基于 DS 同步框架 | 需要理解服务器权威、预测、校正和弱网 |
| 独立完成性能调优 | 要能用 Profiler 数据闭环，而不是只会提出优化点 |
| 配合策划、美术 | 要能将主观表现需求拆成可配置、可验证的系统 |
| 跟进模块缺陷 | 需要较强的问题定位、回归测试和责任意识 |
| 熟悉 ECS | 数据导向和大规模战斗性能是潜在方向 |
| FPS/TPS/MOBA 完整经验优先 | 项目大概率重视联网战斗、枪械或多角色场景 |
| 熟悉 AI 编程工具 | 看重效率，但也会关注候选人的验证和审查能力 |

## 2. 核心技术需求

## 2.1 战斗与 3C

### Character

- 地面和空中运动；
- 加速、减速、急转、惯性；
- 斜坡、台阶、碰撞和接地；
- KCC、CharacterController、Rigidbody 的选择；
- Root Motion 与代码位移；
- 逻辑状态和动画状态的关系；
- 受击、硬直、霸体、打断和取消；
- Locomotion 与 Action 的分层控制。

### Camera

- FPS/TPS 相机；
- 跟随、旋转和碰撞避障；
- 瞄准与锁定；
- 辅助瞄准；
- 后坐力、震屏和镜头反馈；
- 相机状态与战斗状态协作；
- 第三人称枪口和准星方向差异。

### Control

- 输入采样、缓存和消费；
- 按下、按住、释放、短按和长按；
- 连击窗口和预输入；
- 输入重映射；
- 状态控制权仲裁；
- 本地输入与网络命令分离；
- 手感参数数据化。

### Combat

- 技能阶段和时间线；
- 命中检测；
- HitBox/HurtBox；
- 射线与投射物；
- 打断和优先级；
- 伤害、韧性和状态效果；
- 客户端表现与服务器判定；
- 动画事件、逻辑帧和表现时间轴。

## 2.2 枪械与弹道

重点准备：

- Hitscan 和 Projectile 的区别；
- 武器射速和开火节奏；
- 散布；
- 后坐力；
- 弹道下坠；
- 伤害衰减；
- 穿透和爆炸；
- 换弹、切枪和取消；
- 枪口被墙阻挡；
- 准星射线与枪口射线校正；
- 服务端命中验证；
- 高速投射物连续碰撞；
- 特效、声音和相机反馈的即时响应。

## 2.3 DS 与联网战斗

岗位中的 DS 大概率指 Dedicated Server，即专用权威服务器；面试时应主动确认是否为公司内部其他同步框架。

核心问题：

- 客户端发送输入还是状态结果；
- 服务器权威判定；
- 客户端预测；
- 服务器校正；
- 快照插值和外推；
- 命中回溯 Lag Compensation；
- 弱网、延迟、丢包和乱序；
- 断线重连和状态恢复；
- 技能时间轴同步；
- Root Motion 的网络表达；
- 动画表现与网络逻辑解耦；
- 网络带宽与同步频率控制。

### 射击同步高频问题

1. 高速子弹由客户端还是服务器模拟？
2. Hitscan 如何做服务器回溯？
3. 开火表现是否等待服务器确认？
4. 客户端预测命中但服务器否决怎么办？
5. 位置校正如何避免视觉瞬移？
6. 弹丸是否需要逐帧同步？
7. 动画和相机表现是否参与回滚？
8. 断线后需要恢复哪些战斗状态？

## 2.4 性能优化

岗位需要的是数据驱动的优化闭环：

```text
复现问题
→ 建立性能基线
→ 区分 CPU/GPU/内存/网络
→ 定位具体热点
→ 提出最小改动方案
→ 对比优化前后数据
→ 验证 Gameplay 行为一致
```

应准备：

- Unity Profiler Timeline/Hierarchy；
- Profile Analyzer；
- Frame Debugger；
- Memory Profiler；
- GC Alloc；
- Animator 和 Physics 成本；
- 大量角色、子弹和特效；
- 对象池；
- Update 数量；
- Draw Call、SRP Batcher、GPU Instancing；
- Overdraw、阴影和透明特效；
- LOD 和动画降频；
- Jobs/Burst/ECS 的适用边界。

面试回答性能题时不要直接说“使用 ECS”或“加对象池”，应先说明如何测量和定位。

## 2.5 跨职能落地

岗位需要把主观需求转成工程系统，例如：

- “跑步不跟手”拆成输入延迟、加速度、转向速度和动画相位；
- “技能打击感差”拆成命中停顿、镜头、音效、特效和受击反馈；
- “转身不自然”区分 Pose、Root Motion、机械旋转和 CrossFade；
- 把动画资源约束沉淀为导入工具和校验；
- 为策划提供参数、预览、调试和数据验证能力。

## 3. 个人匹配分析

以下结论基于当前 ActionEditor/ARPG Demo 的实际开发内容，正式面试时还要结合真实工作履历。

## 3.1 优势

### 战斗状态机和 3C 方向高度匹配

当前已经实践：

- Locomotion/Action 分层状态机；
- 状态中断、取消和优先级；
- 输入缓存和持续时间；
- 技能系统与状态机协作；
- Movement Policy 仲裁；
- Root Motion 和 KCC；
- 相机相对移动与角色朝向；
- State Timeline；
- 数据驱动配置；
- 运行时诊断和验收矩阵。

有价值的架构观点：

- `StateController` 是状态生命周期唯一真相来源；
- `SkillRuntime` 是技能调度器，不是第二套状态机；
- Action 和 Locomotion 通过显式 Policy 仲裁；
- Animator 不与 KCC 同时拥有机械 Transform；
- 视觉动画和机械运动应当分离。

### 动画系统实践深度较好

已经接触：

- Generic Avatar；
- 独立 FBX 动画；
- Animancer；
- 动画层和 State Weight；
- CrossFade；
- `OnAnimatorMove()`；
- Root Motion 平移和旋转；
- KCC 原子消费；
- 起步、循环、停止和转身；
- 动画资源批量导入；
- 运行时 Root Motion 诊断。

推荐表述：

> 我处理过从动画求值、状态过渡、Root Motion 采集到 KCC 执行的完整链路，也处理过视觉 Pose 混合和机械运动所有权耦合的问题。

### 数据驱动和工具化意识

- 状态时间线；
- 打断轨道；
- 轨道优先级；
- Movement Profile；
- FBX Model/Materials/Rig 批处理；
- 动画 Catalog；
- 配置校验；
- 运行时 Observed 字段；
- 设计文档和测试矩阵。

推荐表述：

> 我的目标不是只把一个角色写通，而是把角色制作流程中重复出现的问题沉淀成编辑器约束、数据校验和运行时诊断能力。

### 问题拆解和验证意识

- 区分视觉模型偏移和机械胶囊位移；
- 区分动画资源、Animator 求值和 KCC 执行；
- 通过 A/B 测试验证 CrossFade；
- 追踪 Animancer → Animator → RootMotionSource → KCC；
- 不把未经验证的推测当成结论；
- 倾向生产级修复，而不是角色特例。

## 3.2 短板和风险

### DS 和网络同步可能是最大短板

当前工程尚未充分体现：

- Dedicated Server 实战；
- 客户端预测；
- 服务器校正；
- 弱网模拟；
- 丢包和乱序；
- 断线重连；
- Lag Compensation；
- 回滚；
- 网络带宽优化。

如果没有真实项目经验，应诚实表述：

> 我目前最深入的实践集中在战斗、3C、状态机、动画和工具链。网络同步方面掌握基本架构和问题模型，但生产环境中的弱网、断线重连和服务器权威实战是需要继续补齐的部分。

可强调现有架构向网络同步迁移的基础：

- 输入与执行分离；
- 状态数据化；
- 机械根单一所有权；
- 视觉和机械运动分离；
- 时间线和状态可序列化；
- 明确的状态切换上下文。

### 枪械和弹道经验可能不足

当前项目偏 ARPG，需要补充射击专项准备。

可强调迁移关系：

| ARPG 经验 | 射击对应能力 |

| Skill Config | Weapon Config |

- 普通 GameObject 组件化；

- 自研 ECS；

- Baking/SubScene/System Group/ECB。

没有项目经验时，不应把普通组件架构包装成 ECS。

- Update 与 FixedUpdate；
- Rigidbody、CharacterController、KCC；
- CCD；
- Cast/Overlap/Trigger；
- 高速投射物；
- 接地、斜坡和台阶；
- 物理查询性能。

渲染重点：

- Draw Call；
- SRP Batcher；
- GPU Instancing；
- Overdraw；
- 阴影；
- LOD；
- Frame Debugger；

### 商业项目交付证据

面试官很可能追问：

- 是否有上线项目；

## 4. 项目案例准备

每个案例使用 STAR 结构，控制在 3～5 分钟。

## 4.1 状态机架构

### Situation

技能系统、角色状态和动画容易形成多套状态真相，导致生命周期和运动策略互相争夺。

### Task

建立可扩展的分层状态机，统一状态切换、打断、动画和运动策略。

### Action

- `StateController` 作为唯一状态真相；
- Locomotion/Action 分层；
- Skill 向 State 提交请求，State 向 Skill 发送通知；
- Movement Policy 按层优先级仲裁；
- 打断轨道具备可视化顺序和运行时优先级；
- 默认空 Action 状态不影响 Locomotion。

### Result

- 避免双状态机；
- 状态切换和运动控制可追踪；
- 策划可以通过数据配置中断；
- 为技能取消和多层动画提供统一基础。

## 4.2 Root Motion 与 KCC

### Situation

Animator 与 KCC 都可能影响角色根，动画过渡还会混合 Root Motion，出现位置和旋转不一致。

### Task

建立单一 Transform 所有权和可诊断 Root Motion 管线。

### Action

- Animator/Animancer 只负责求值；
- `OnAnimatorMove()` 捕获 Delta；
- 位移和旋转原子消费；
- KCC 唯一执行机械位移和碰撞；
- Root Motion 旋转直接提交，不经过普通角速度限制；
- Yaw-only 过滤；
- 运行时显示 Pending/Consumed Delta；
- 将视觉 Pose CrossFade 与机械 Root Motion 所有权分离。

### Result

- 能区分视觉偏移和机械位移；
- 能定位动画过渡中的 Root Motion 问题；
- 管线支持 Root Motion 位移、转身和 KCC 碰撞。

注意：如果相关优化尚未完成，不要宣称问题已经彻底解决。应说明已定位的根因、验证过程和当前演进方向。

## 4.3 输入和状态打断

### Situation

换向经过摇杆中心时会产生单帧零输入，错误触发停止状态。

### Action

- 记录 Move Input Active/Inactive Duration；
- 中断条件支持最短持续时间；
- 增加角色前向与输入方向夹角条件；
- 轨道顺序映射运行时优先级；
- 拖拽采用松手交换，避免编辑过程中反复重排。

### Result

- 避免单帧输入噪声误触发；
- 急转、停止和 Turn Back 可独立配置；
- 编辑器表达和运行时行为一致。

## 4.4 工具化和资产流程

### Situation

大量独立 FBX 导入设置不一致，手工处理成本高且容易出错。

### Action

- 建立 Model/Materials/Rig 三阶段批处理；
- 统一 Generic Avatar；
- 控制模型、材质和 Rig 导入项；
- 增加动画 Catalog 和运行时资源查找；
- 对配置和组件重复进行校验。

### Result

- 降低动画资源接入成本；
- 减少 Avatar 和 Root Motion 配置错误；
- 将一次性修复沉淀为生产工具。

## 6. AI 编程工具加分项

不建议说：

> 我用 AI 帮我写代码，所以开发很快。

建议表达：

## 8. 面试表达策略

### 8.1 推荐定位

> 擅长 Unity 战斗 Gameplay、3C、动画和工具链，具备把复杂表现问题拆解为状态、动画、机械运动和数据管线问题的能力。

### 8.2 回答结构

技术问题尽量按以下结构：

```text
目标和约束
→ 核心数据与所有权
→ 系统边界
→ 主流程
→ 异常与降级
→ 调试手段
→ 性能考虑
→ 验收方式
```

避免只列 API 或设计模式。

### 8.3 不要过度包装

- 没有 DS 实战就不要包装为生产经验；
- 没有 DOTS 项目就不要把组件化称为 ECS；
- 尚未完成的问题不要宣称已彻底解决；
- 不知道公司内部框架时先确认术语；
- 性能优化必须给指标或说明测量方法。

### 8.4 把短板转为可迁移能力

例如网络经验不足时：

> 我没有把概念包装成生产经验，但我当前状态、输入和机械运动的设计已经在主动满足可序列化、可回放和单一所有权，这些是客户端预测和服务器校正需要的基础。我也会优先补齐贵项目实际采用的同步模型。

## 10. 最终结论

该岗位和当前 ActionEditor 技术主线高度契合。主要优势是：

- 战斗状态机；
- 3C；
- 动画与 Root Motion；
- KCC；
- 数据驱动；
- 编辑器工具链；
- 复杂问题拆解和运行时诊断。

主要风险是：

- Dedicated Server 生产经验；
- 弱网和断线；
- 枪械与弹道；
- ECS/DOTS 深度；
- 商业项目完整交付证据。

面试成败很可能取决于两点：

1. 能否把现有 3C、动画和战斗架构讲得清晰、具体且可信；
2. 面对网络和射击短板时，能否诚实说明边界，并展现快速理解同步模型和迁移现有架构能力。

差异化价值不只是“会写 Unity Gameplay”，而是：

> 能从状态所有权、动画求值、机械运动、数据配置、调试工具和生产流程多个层面建设一套可长期迭代的战斗系统。
