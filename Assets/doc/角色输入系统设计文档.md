# 角色输入系统设计文档

## 1. 目的

当前 `State` 运行时里的输入处理仍然是临时实现：

1. 直接在 `SkillPlayerController` 内部读取 `Input.GetKey/GetKeyDown/GetKeyUp`
2. `移动输入` 只等于 `W/A/S/D/方向键` 是否按下
3. `Skill`、`State`、角色移动都各自从输入层取数据，没有统一快照

这套方式不足以支持正式开发，尤其不适合后续接入：

1. `KCC`
2. 正式角色控制器
3. 复杂打断条件
4. 组合键/预输入/缓冲输入
5. 可替换的输入后端

因此需要建立一个独立于 `SkillEditor` 的角色输入系统。

核心原则：

1. 输入系统写在 `SkillEditor` 之外
2. `SkillEditor` 只消费输入系统输出的数据，不负责采集输入
3. 角色移动、状态机、技能运行时共用同一份输入快照
4. 设计参考 `AsiActionEditor`，但不照搬其老式结构

## 2. 参考依据

### 2.1 AsiActionEditor 的可复用思路

参考代码：

1. `Assets/Plugins/AsiActionEditor/Client/RunTime/Script/Preview/ActionEngineSingleEnvironment/Manager/ActionEngineManager_Input.cs`
2. `Assets/Plugins/AsiActionEditor/Engine/RunTime/Script/AsiActionEditor/RunTime/Script/UnitController/ActionStateMachine/ActionStateMachine.cs`
3. `Assets/Plugins/AsiActionEditor/Engine/RunTime/Script/AsiActionEditor/RunTime/Script/UnitController/ActionStateMachine/ActionStateMachine.TimeLine.cs`
4. `Assets/Plugins/AsiActionEditor/Engine/RunTime/Script/AsiActionEditor/RunTime/Script/UnitController/ActionStateMachine/Part/ActionStatePart.InputCheck.cs`

可以保留的思路：

1. 输入采集与状态机判断分离
2. 需要同时维护：当前输入状态、按下、抬起、点击、长按、预输入
3. `移动输入中` 与 `移动方向` 应该是明确的运行时数据，不应由每个条件自行重算
4. 状态机不直接拥有输入设备，只接收输入结果

### 2.2 不照搬的部分

不建议直接复制 `AsiActionEditor` 的原因：

1. 它把输入、预览环境、相机、状态机耦合得比较紧
2. 当前项目后续要接 `KCC`
3. 当前项目需要让 `Skill`、`State`、角色控制共享统一输入层
4. 当前项目更适合做成独立服务 + 快照接口，而不是巨大 manager

## 3. 设计目标

本轮输入系统设计要明确解决以下问题：

1. 建立统一主链路：`按键 -> 变量 -> 事件 -> 行为`
2. 为角色生成统一输入快照和输入变量状态
3. 给 `KCC` 提供移动/朝向输入
4. 给 `State` 提供打断所需输入条件
5. 给 `Skill`、被动技能、槽位系统提供统一动作事件
6. 支持 PC、手柄、移动端的统一行为映射
7. 提供独立输入配置界面，用于配置行为和对应键位

本轮先不直接实现：

1. 网络输入同步
2. 输入录制回放工具
3. 动画位移和 root motion 处理

---

## 4. 核心原则

### 4.1 输入系统必须在 SkillEditor 之外

建议新建独立运行时模块，例如：

1. `Assets/GamePlay/InputSystem/Runtime`

不要放到：

1. `Assets/SkillEditor/...`

原因：

1. 输入系统是角色运行时基础设施，不是技能编辑器附属功能
2. `KCC`、角色控制器、摄像机、交互系统也会依赖它
3. `SkillEditor` 应该只通过接口读取输入数据

### 4.2 角色移动、状态机、技能必须共享同一输入快照

不能出现：

1. `KCC` 用一套输入结果
2. `State` 用另一套 `Input.GetKey`
3. `Skill` 再自己扫一遍键盘

否则一定会出现：

1. 明明角色已经在移动，状态机判定却说没移动
2. 明明技能按键触发了，状态打断没收到对应事件
3. 同一帧多个系统看到的输入状态不一致

### 4.3 输入系统输出的是“意图”，不是直接行为

输入系统应输出：

1. 角色是否存在移动意图
2. 角色移动方向
3. 视角变化
4. 具体动作按键事件
5. 组合键事件

输入系统不直接负责：

1. 驱动动画
2. 切换状态
3. 释放技能
4. 推进角色位移

这些由上层系统消费输入意图后自行决定。

### 4.4 输入主链路必须固定为“按键 -> 变量 -> 事件 -> 行为”

这是当前项目输入系统最关键的设计约束。

完整链路应固定为：

1. 设备按键或触摸输入
2. 写入输入变量
3. 由输入变量变化产生输入事件
4. 运行时系统监听事件并触发行为

#### 示例 1：移动输入

链路应为：

1. 玩家推动摇杆或按下 `W/A/S/D`
2. 输入系统更新 `MoveAxis / HasMoveInput / MoveVector`
3. 输入系统发出 `MoveStarted / MoveUpdated / MoveStopped`
4. `KCC` 消费移动变量推进位移
5. `State` 消费移动事件或移动变量，把 `idle` 切到 `run`

这里要强调：

1. `State` 看到的是“移动输入变量/事件”
2. 不是直接自己去扫键盘

#### 示例 2：技能槽位与被动监听

链路应为：

1. 玩家按下 `按键1`
2. 输入系统把它解释为 `Action = SkillSlot1`
3. 输入系统发出 `InputActionTriggered(SkillSlot1)`
4. 槽位系统根据 `SkillSlot1` 找到装配技能，例如 `Skill_001`
5. 技能系统发出 `SkillCastRequested(Skill_001)`
6. 技能正式释放后再发出 `SkillCastStarted(Skill_001)` 或 `SkillCastSucceeded(Skill_001)`
7. 被动技能监听到 `Skill_001` 释放事件，触发“攻击力提高 20%”

关键点：

1. 输入系统不直接释放某个具体技能
2. 输入系统只发送“行为动作事件”
3. 槽位和技能系统再把“动作”解释成具体技能行为

### 4.5 行为优先于设备键位

输入系统中最稳定的配置单位不是键位，而是“行为”。

例如：

1. `Attack`
2. `SAttack`
3. `Jump`
4. `Dodge`
5. `Lock`
6. `SkillSlot1`
7. `SkillSlot2`
8. `SkillSlot3`
9. `Move`

设备键位只是在不同平台下映射到这些行为。

这意味着配置方式应始终是：

1. 先定义行为
2. 再为行为配置 PC / 手柄 / 移动端映射

而不是反过来先定义某个键，再在代码里硬编码它代表什么行为。

## 5. 运行时分层

建议拆成 4 层。

### 5.1 设备层

负责从真实设备或 Unity Input System 获取原始输入。

建议接口：

```csharp
public interface IRawCharacterInputSource
{
    Vector2 ReadMoveAxis();
    Vector2 ReadLookAxis();
    bool GetButton(string actionName);
    bool GetButtonDown(string actionName);
    bool GetButtonUp(string actionName);
}
```

这一层建议优先基于 Unity 新 Input System 实现。

原因：

1. 原生支持 PC / 手柄 / 移动端
2. 原生支持 Action Map 与不同 Control Scheme
3. 后续接 UI 重绑定、移动端虚拟摇杆会更顺

这一层可替换：

1. 旧 `Input` API
2. 新 Input System
3. AI/录制回放输入

### 5.2 变量层

这一层负责维护输入变量，不直接面向业务系统。

建议维护的变量至少包括：

```csharp
public struct CharacterInputVariables
{
   public Vector2 MoveAxis;
   public Vector3 MoveVectorWorld;
   public Vector3 MoveVectorLocal;
   public bool HasMoveInput;
   public bool HadMoveInputLastFrame;

   public Vector2 LookDelta;

   public bool AttackHeld;
   public bool AttackDown;
   public bool AttackUp;

   public bool JumpHeld;
   public bool JumpDown;
   public bool JumpUp;

   public bool DodgeHeld;
   public bool DodgeDown;
   public bool DodgeUp;

   public bool SkillSlot1Held;
   public bool SkillSlot1Down;
   public bool SkillSlot1Up;
}
```

这一层的职责是：

1. 把原始输入转成稳定变量
2. 维护当前帧与上一帧对比
3. 提供给事件层生成事件

### 5.3 事件层

事件层根据变量变化生成业务可消费的输入事件。

建议事件类型：

1. `MoveStarted`
2. `MoveUpdated`
3. `MoveStopped`
4. `ActionStarted`
5. `ActionPerformed`
6. `ActionCanceled`
7. `SkillSlotTriggered`
8. `ComboTriggered`

建议结构：

```csharp
public struct CharacterInputActionEvent
{
   public string ActionName;
   public CharacterInputEventPhase Phase;
   public float Time;
   public int Frame;
   public Vector2 AxisValue;
   public Vector3 WorldValue;
}
```

### 5.4 解释层

把变量和事件解释成游戏语义输入快照。

输出示例：

```csharp
public struct CharacterInputSnapshot
{
    public int Frame;
    public float Time;

   public CharacterInputVariables Variables;

    public Vector2 MoveAxis;
    public Vector3 MoveVectorWorld;
    public Vector3 MoveVectorLocal;
    public bool HasMoveInput;
    public bool HadMoveInputLastFrame;

    public Vector2 LookDelta;
    public Quaternion CameraYaw;

    public bool JumpHeld;
    public bool JumpDown;
    public bool JumpUp;

    public bool DodgeHeld;
    public bool DodgeDown;
    public bool DodgeUp;

    public bool SkillPrimaryHeld;
    public bool SkillPrimaryDown;
    public bool SkillPrimaryUp;
}
```

这一层需要维护：

1. 当前帧状态
2. 上一帧状态
3. `Down/Up/Hold`
4. 预输入缓存
5. 组合输入缓存

### 5.5 分发层

把同一份输入快照分发给各运行时系统。

建议接口：

```csharp
public interface ICharacterInputProvider
{
    CharacterInputSnapshot Current { get; }
    bool TryGetActionEvent(string actionName, out CharacterInputActionEvent actionEvent);
}
```

消费者包括：

1. `KCC` 运动驱动
2. `StateController`
3. `SkillPlayerController`
4. 交互系统

### 5.6 适配层

把统一输入快照适配给具体系统。

例如：

1. `KccInputAdapter`
2. `StateInputAdapter`
3. `SkillInputAdapter`

这样 `SkillEditor` 只看到适配后的结构，不依赖底层输入实现。

## 6. 与 KCC 的集成方式

### 6.1 KCC 是位移主导者

至少在本阶段：

1. 常规移动状态下，由 `KCC` 主导角色位移
2. 输入系统给 `KCC` 提供移动意图和朝向意图
3. `State` 根据同一份移动意图决定状态切换

这意味着：

1. `idle -> run` 不应通过动画 root motion 推角色跑起来
2. 而应先由输入驱动 `KCC` 运动
3. 再由状态切换驱动播放 `run` 动画

### 6.2 需要输出给 KCC 的数据

输入系统至少提供：

1. `MoveVectorWorld`
2. `MoveVectorLocal`
3. `HasMoveInput`
4. `LookDelta`
5. 当前相机 yaw 或目标朝向

这样 KCC 与状态机看到的是同一份移动意图。

## 7. 与 State 的集成方式

### 7.1 State 不再自己读 Input.GetKey

后续应删除当前 `SkillPlayerController.CaptureStateInputSnapshot()` 中对：

1. `Input.GetKey`
2. `Input.GetKeyDown`
3. `Input.GetKeyUp`

的直接依赖。

改为从 `ICharacterInputProvider` 构造：

```csharp
public struct StateInputSnapshot
{
    public string DownAction;
    public string UpAction;
    public string ClickAction;
    public string HoldAction;
    public bool IsMoveInput;
    public bool IsMoveInputPre;
    public Vector3 MoveVectorWorld;
    public Vector3 MoveVectorLocal;
}
```

### 7.2 State 打断条件需要两类移动条件

参考 `AsiActionEditor`，至少要支持：

1. `MoveState`
   - 移动输入中
   - 无移动输入
   - 预输入成立
2. `MoveDirection`
   - 前
   - 后
   - 左
   - 右
   - 或者与角色朝向/相机朝向的夹角区间

否则正式项目里无法稳定表达：

1. `idle -> run`
2. `run -> runEnd`
3. `frontDodge / backDodge / sideStep`

### 7.3 预输入要像 AsiActionEditor 一样是被消费的

`AsiActionEditor` 里 `IsMoveInputPre` 不是永久标记，而是在输入检查完成后会被消费清理。

本项目建议保持这个原则：

1. 预输入是短生命周期窗口
2. 被状态机消费后应清理
3. 不能把“上一帧有移动输入”长期冒充预输入

## 8. 与 Skill 的集成方式

`Skill` 不应该知道键盘键位，只应该知道动作语义和槽位语义。

例如：

1. `SkillPrimary`
2. `SkillSecondary`
3. `Dodge`
4. `Jump`
5. `Interact`
6. `SkillSlot1`
7. `SkillSlot2`
8. `SkillSlot3`

输入系统负责把：

1. 实际设备按键
2. 键位映射
3. 长按/短按
4. 组合键

解释成动作事件，再交给 `SkillPlayerController`。

这与旧文档中“输入系统不直接释放技能，而是发送事件”的原则一致。

### 8.1 槽位语义应该成为正式输入动作

对于正式项目，建议把：

1. `SkillSlot1`
2. `SkillSlot2`
3. `SkillSlot3`
4. `SkillSlot4`

定义成正式输入行为，而不是把 `Q/E/R/F` 这类键位写死在技能系统里。

这样：

1. PC 可以是 `1/2/3/4`、`Q/E/R/F`、鼠标侧键
2. 手柄可以是 `X/Y/B/A` 或肩键
3. 移动端可以是 UI 按钮

但运行时技能系统只看到统一动作：

1. `SkillSlot1 Triggered`
2. `SkillSlot2 Triggered`

### 8.2 被动技能监听的是技能事件，不是输入事件

例如“技能1释放后攻击力提高 20%”，推荐事件链如下：

1. 输入系统发出 `SkillSlot1 Triggered`
2. 槽位系统解析得到 `Skill_001`
3. 技能系统发出 `SkillCastStarted(Skill_001)`
4. 被动技能监听 `SkillCastStarted(Skill_001)`
5. 执行增益行为

这样可以避免：

1. 技能更换槽位后被动逻辑失效
2. 不同角色键位不同导致被动触发条件错乱

## 9. 推荐实现结构

建议新增以下运行时对象：

1. `CharacterInputService`
2. `CharacterInputVariables`
2. `CharacterInputSnapshot`
3. `CharacterInputActionEvent`
4. `IRawCharacterInputSource`
5. `ICharacterInputProvider`
6. `StateInputAdapter`
7. `SkillInputAdapter`
8. `KccInputAdapter`
9. `InputActionDefinition`
10. `InputBindingProfile`
11. `InputActionMapConfig`

建议目录：

1. `Assets/GamePlay/InputSystem/Runtime`
2. `Assets/GamePlay/InputSystem/Runtime/Adapters`
3. `Assets/GamePlay/InputSystem/Runtime/Providers`
4. `Assets/GamePlay/InputSystem/Config`
5. `Assets/GamePlay/InputSystem/Editor`

### 9.1 推荐配置对象

建议至少有三类配置资源。

#### 行为定义

定义有哪些行为。

例如：

1. `Attack`
2. `SAttack`
3. `Lock`
4. `Jump`
5. `Dodge`
6. `Defense`
7. `SkillSlot1`
8. `SkillSlot2`
9. `SkillSlot3`
10. `Move`

#### 平台映射

为不同行为配置不同平台的绑定。

例如 `Attack`：

1. PC -> 鼠标左键
2. 手柄 -> `X`
3. 移动端 -> `AttackButton`

#### 行为列表

维护哪些行为会进入运行时输入系统，以及它们的默认属性。

例如：

1. 是否是轴向行为
2. 是否允许长按
3. 是否允许组合输入
4. 是否能进入预输入缓存

### 9.2 配置界面要求

参考你提供的界面草图，配置界面至少要分成两个页签：

1. `按键配置`
2. `行为列表配置`

#### 行为列表配置

这一页负责：

1. 添加行为
2. 删除行为
3. 修改行为名
4. 定义行为类型

展示上应类似：

1. 左侧或列表区显示行为列表
2. 每条行为可删除
3. 顶部有 `添加 InputAction`

#### 按键配置

这一页负责：

1. 为键盘配置行为
2. 为鼠标配置行为
3. 为手柄配置行为
4. 后续为移动端配置 UI 输入映射

建议分组：

1. 键盘按键配置
2. 鼠标按键配置
3. 手柄按键配置
4. 连击按键配置
5. 移动端按键配置

每一行配置至少包含：

1. 输入源键位
2. 目标行为下拉框
3. 删除按钮

每个分组应提供：

1. `+` 添加映射
2. `-` 删除映射

底部应提供：

1. `保存所有配置`

### 9.3 平台支持顺序

实现优先级建议是：

1. PC
2. 手柄
3. 移动端

移动端可以晚做运行时接入，但设计和配置结构应现在就预留。

原因：

1. 行为定义和平台映射模型一开始就应统一
2. 否则后续补移动端时会再次改配置结构

## 10. 分阶段落地建议

### 10.1 第一阶段

目标：先建立最小可用输入系统，让 `State` 打断和 `KCC` 移动使用统一输入快照。

完成内容：

1. 建立 `CharacterInputService`
2. 建立行为定义与平台映射数据结构
3. 输出 `HasMoveInput`、移动向量、动作 `Down/Up/Hold`
4. `SkillPlayerController` 改为依赖输入服务
5. `StateMoveInputInterruptCondition` 改为消费输入快照

### 10.2 第二阶段

目标：补足正式项目所需的技能输入语义和配置界面。

完成内容：

1. 输入系统配置界面
2. 长按/短按
3. 组合键
4. 输入缓冲
5. 动作名到键位的映射配置
6. 槽位动作到技能事件链路

### 10.3 第三阶段

目标：补足高级状态条件和多平台后端。

完成内容：

1. 方向型打断条件
2. AI 输入源
3. 回放输入源
4. 网络同步输入源
5. 移动端 UI 输入映射

## 11. 当前代码需要的直接改造点

后续正式实现时，至少要改以下位置：

1. `SkillPlayerController`
   - 删除直接 `Input.GetKey` 读取
   - 改为依赖输入服务
2. `StateInputSnapshot`
   - 扩充移动向量和动作语义字段
3. `StateMoveInputInterruptCondition`
   - 改为严格对齐移动输入语义
4. 新增方向型输入条件
5. `Skill` 触发逻辑
   - 改为消费动作事件，而不是直接绑死设备键位

## 12. 结论

后续正式方案应是：

1. 输入系统独立于 `SkillEditor`
2. `KCC`、`State`、`Skill` 共用统一输入快照
3. 输入主链路固定为 `按键 -> 变量 -> 事件 -> 行为`
4. `SkillEditor` 只消费输入系统，不拥有输入采集逻辑
5. 输入配置以“行为”为中心，而不是以设备键位为中心
6. PC、手柄、移动端共享同一套行为定义，只在映射层区分设备
7. 设计参考 `AsiActionEditor` 的输入语义和预输入思路
8. 运行时结构按现代项目方式拆成独立服务、事件层与适配层
